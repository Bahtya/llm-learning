## 试驾报告式读法：MTP/DFlash/DSpark 实测通读

"某方案快 2 倍"和"这车极速 300 km/h"是同一类话术：听着猛，但你不知道市区油耗多少、满载爬坡行不行。UP 主那份 MTP/DFlash/DSpark 实测值得抄的作业不是"谁第一"，而是它的实验设计——场景分了三档、N 值扫了一条曲线、代价摆了三张账单。学会读它，你就能读任何一份加速对比。

先对齐名词：投机解码的 draft-verify 框架与三种方案的出身见[投机解码](#/v3/06)，本章只讲"怎么读实测"。

### 读法一：先看自变量设计

可信的对比，自变量必须铺满"任务确定性（determinism）"这条因果链：答案越唯一 → 草稿与主模型一致的概率（**接受率**，acceptance rate）越高 → 每步校验留下的 token 越多 → **加速比**（speedup）越大。所以场景要选在确定性坐标的两端和中间：

- 科学计算——数学题答案只有一个，确定性最高；
- 代码工程——实现路径相对固定，居中（Agent 场景里最多的正是这类负载）；
- 创意写作——怎么写都行，最发散。

粗略换算：加速比 ≈ 1 + N × 接受率——线性上界口径（严格式 1+p+…+p^N，见 [投机解码](#/v3/06)），N 是一次猜的 token 数（DSpark 里叫 gamma 值）。横轴取 N、纵轴取输出速度；对比必须在同一框架内做（SGLang 一组、llama.cpp 一组，两派背景见[推理框架两流派](#/v3/02)），这就是控制变量（control variables）。

> **案例（视频出处：BV1qGh56JEj2）** 三场景实测排名与接受率排序完全一致：科学计算接受率最高、加速最快；代码工程路径固定、接受率还可以；创意写作最发散、加速比最小。同一框架（SGLang）内加速排名：DSpark > MTP > 刚出第二代的 dFlash。UP 主研究 dFlash 一代大半年，评二代"快，但那是傻快"——出字快不等于赚，接受率才是分母。

### 读法二：曲线形状本身就是结论

峰值在哪是次要点，曲线怎么弯才是重点：

- 先升后降：猜得越多，混进错的概率越大，从第一个错处截断就白猜，所以必然存在**甜点区间**（sweet spot）；
- 单调上升：草稿质量扛得住更大的 N；
- 随 N 下降：接受率太低，多猜纯属浪费。

> **案例（视频出处：BV1qGh56JEj2）** 换到 llama.cpp 结论类似，甜点在一次猜 2/3/4 个；MTP 随 N 增大持续走高，3、4、5 直到 7 还在涨；DSpark 峰值落在 5/6/7；而代码场景下 dFlash 和 DSpark 随 N 增大反而下降。实测主模型是 64 层的千问（Qwen），字幕转写作 27B，层数对得上 Qwen3-32B。三条形状不同的曲线，把"草稿质量决定天花板"直接画了出来。

### 读法三：翻三张隐藏账单

加速比只是封面数字，底页还有三笔：

1. **Prefill 账**：草稿也要吞一遍你的输入，Decode 提速必然伴随 Prefill 降速——两阶段的分工见[Prefill 与 Decode](#/v1/07)；
2. **显存账**：dFlash/DSpark 要额外挂草稿模型（draft model），MTP 只在权重里多一层；
3. **兼容账**：多卡部署方式会直接砍掉你的选项。

> **案例（视频出处：BV1qGh56JEj2）** UP 主原话"投机解码不是免费的"：能加速 Decode，但"肯定会降低你的 Prefill 的速度"。巅峰显存对比里 dFlash/DSpark 因草稿模型明显更吃显存，MTP 最轻量；跑这个量级的模型 24G 已经不够、32G 可以（单卡多卡均可）——新增开销从哪本账扣，见[显存三本账](#/v4/02)。另一个坑：[流水线并行](#/v4/06)（PP，Pipeline Parallelism）拆分下仍可用 DSpark，当前框架却用不了 MTP，选型前先确认部署形态。

把这套读法压成一张检查清单：

| 维度 | 要问的问题 | 本章案例的答案 |
| --- | --- | --- |
| 场景 | 分了几档确定性？ | 科学/代码/创意三档 |
| N 值 | 横轴扫了吗？ | llama.cpp 甜点 2~4，DSpark 5~7 |
| 框架 | 同框架内比吗？ | SGLang 与 llama.cpp 各一组 |
| 代价 | Prefill/显存报了吗？ | Prefill 必降；草稿模型吃显存 |
| 部署 | 兼容你的并行方式吗？ | PP 下可用 DSpark、不可用 MTP |

结论一句话：**看实测对比，先审实验设计，再看峰值数字**——设计不合格的曲线，峰值再高也别抄。

## 怎么验证

- **复现自己的 N 值曲线**：固定一组 prompt，llama.cpp 用 `--draft-max` 取 2/4/6/8 各跑一遍，从返回 JSON 的 `timings.predicted_per_second` 读输出速度画成曲线，找你机器上的甜点，再对照 2/3/4 与 5/6/7 看偏了多少。
- **反推接受率**：用"开/不开投机解码"的速度比得到加速比，按 (加速比 − 1) ÷ N 近似反解接受率，看你的任务落在科学、代码、创意哪一档。
- **分场景对照**：备三组 prompt（数学题、写脚本带 tool call、写散文）各扫一遍 N，验证"确定性越高，甜点越靠右"。
- **量两笔隐藏账**：开与不开各记一次 `timings.prompt_ms`（Prefill 代价）和 `nvidia-smi --query-gpu=memory.used --format=csv`（显存峰值）；再到模型目录的 `config.json` 里搜 `mtp`，确认是否内嵌 MTP 层、能否配合你的 PP 部署。
