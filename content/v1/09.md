## 全员到岗的稠密，与按需叫号的专家

稠密（dense）模型像一位全科医生坐诊：每个 [token](#/v1/01) 来了，模型里**所有**参数都要为它过一遍，参数越多每步越贵。MoE（Mixture of Experts，混合专家）换了编制：医院养一大群专科医生，但每个病人来了，分诊台只挑两三位接诊，其余专家这单不干活。**参数都在编（都得占地方），干活的人却很少**——本章就要分清这两个数：总参数量与激活参数量。

## FFN 层 = 专家层

回顾 [Transformer：按层堆叠的机器](#/v1/03)，每层 = 注意力 + FFN。MoE 只动 FFN 这一半：把那一个 FFN 换成 N 个并列的 FFN，每个叫一个专家（expert）；前面加一个路由器（router，也称门控网络）给每个 token 打分，只送往得分最高的 top-k 个专家。注意力层照旧，token 之间还是互相看（[注意力](#/v1/04)）。这种"绝大多数参数不参与当前计算"的设计叫稀疏激活（sparse activation）。

于是同一个模型有两个"大小"：**总参数量**（total parameters）决定要装多少权重——路由器随时可能把 token 派给任何专家，谁都得常驻待命；**激活参数量**（activated parameters）决定每个 token 实际算多少。命名直接写在型号里：Qwen3-30B-A3B 的 **A3B 就是 Activated 3B**——总参数 30B，每个 token 只激活 3B。

> **案例（视频出处：BV14UEY6WEW7）**
> UP 主拆"96G 畅跑 70B"话术时的关键数字：如今的 200B 级模型"乍一看它 200B，但其实可能只是 A10B，激活量只有 10B"。所以 DeepSeek V4 Flash 这类模型，一台 128G 内存的 Strix Halo（AMD 统一内存 APU 平台，APU 即把 CPU 和显卡装进同一颗芯片，见 [统一内存与 offloading](#/v4/08)）就能畅快地跑，"不一定需要这样的大显存显卡"。**算力账看激活参数，容量账看总参数。**

## 为什么 MoE 对算力要求不高，却吃显存和内存

- **算的账按激活参数记**：[decode](#/v1/07) 每吐一个 token，只把被选中那几个专家的权重从显存搬出来算（[带宽决定 Decode](#/v4/03)）。激活 3B~10B，每步计算量和搬运量都不大，入门级算力也喂得动。
- **装的账按总参数记**：30B 总参按 FP16 算就是 30B × 2 字节 ≈ 60G（[显存三本账](#/v4/02)），一个专家都不能缺席。

所以 MoE 的画像是"**算得动，装不下**"。路由本身还有开销：实测 MoE 吐字速度不是恒定的，因为"内部有路由、各种各样复杂的机制"；多卡部署时路由信息在卡间来回传导，会把容量和带宽优势吃掉，大量调度还压在 CPU 上。所以说"统一内存天生就是为了 MoE 来设计的"——容量大、碎片化低（详见[统一内存与 offloading](#/v4/08)）。

> **案例（视频出处：BV1otY26LE8w）**
> DeepSeek V4 Flash 总参数 200 多 B、"激活量只有 10B"——计算量小，但内部调度极其复杂。一个月后的 V4.1 参数翻倍到五六百 B，权重约 500G，"里面有 200 个 G 就是这个 n-gram（连续 n 个 token 组成的短语，这里是查询表）"——MoE 变大时，"装的部分"比"算的部分"膨胀得快。

## n-gram 查询表：可以外挂的部分

新一代 MoE 还把一部分参数做成 n-gram 查询表（n-gram lookup table）：不参与矩阵乘，只被"查"，访问频率低——不是每步都用，就不必常驻最贵的显存，可以 offload（卸载）到内存、硬盘甚至 U盘（层级见[显存 vs 内存](#/v4/01)）。

> **案例（视频出处：BV1xQtf6SEHR）**
> 176B 的 Qwen3.8-Flash 分两部分：**125B 主模型常驻显存，51B 是 n-gram 查询表外挂**。UP 主只有 48G 显存，来自两张 24G 魔改 10 系卡：P40 + P106（P106 原版 6G，这里用的是 24G 魔改版）。矿卡=挖矿退役的便宜卡，[显卡市场生存指南](#/v4/10) 详解；P40/P106 是十年前的老卡，代际见 [架构代际](#/v4/04)。16G 内存装不下查询表、100G 硬盘放不下模型（还要放系统、缓存与 KV，且需整块连续空间），最后放进 100 元的 128G 高速 U盘。实测不开 MTP、不开任何[投机解码](#/v3/06)，解码 28~29 tok/s，prefill 314 tok/s（llama.cpp 日志可查），Q4 量化的 [KV 缓存](#/v1/05)开到 160K 上下文。

账走通了：176B 是总参数，决定"先找到放 72G 的地方"——72G = 主模型约 21G（压得极狠的 IQ 档）+ 查询表约 51G（只浅压），量化档位见 [GGUF 档位](#/v2/03)，完整算账见 [176B MoE + U盘案例](#/v5/05)；激活部分小，决定"两张十年前的老卡也喂得动"；查询表不常被查，还能再往慢介质挪。同显存的常规玩法就是"跑一个 30B 的 A3B MoE"——拆出外挂后，176B 也能进门。

## 怎么验证

- 读 Hugging Face 的 `config.json`：`num_local_experts`（专家总数）、`num_experts_per_tok`（每 token 选几个专家），有这两个字段就是 MoE。
- 型号即账本：Qwen3-30B-A3B = 总 30B、激活 3B；FP16 权重 ≈ 总参数 × 2 字节 ≈ 60G，`ls -lh` 看权重文件量级能否对上。
- llama.cpp 加载 MoE 的 GGUF，启动日志打印 `n_expert` 与 `n_expert_used`——专家总数与每 token 实际启用数，路由 top-k 一目了然。
- 单并发跑 Qwen3-30B-A3B，输出速度（口径见 [tok/s](#/v3/01)）应与 3B 稠密小模型同量级——显存占用却天壤之别。
