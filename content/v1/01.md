## 模型不认识字，只认识编号

遇到看不懂的词，先查[术语速查表](#/v6/02)；"怎么验证"小节需要本地模型环境，没有环境可跳过，不影响后续阅读。

把大模型想成一个只认编号的图书馆管理员：你递给它一串编号，它查表处理，回给你的也是一串编号。先交代一个全书高频词：**推理**（inference）= 拿训练好的模型来生成回答的过程（你在聊天窗口等回复，模型干的就是推理），与"训练"相对。文本进模型之前，要先被切成小片段，每个片段对照一张总表换成一个整数；模型吐出来的整数，再对照同一张表换回文字。这个小片段叫 **token**（词元），那张总表叫 **词表**（vocabulary），切碎并换成编号的过程叫 **分词**（tokenize），编号换回文字叫 **反分词**（detokenize），换出来的整数就是 **token id**。

为什么不直接按"字"或"词"切？两头都不划算：按单字符切，序列太长，后面所有计算都跟着吃亏；按整词切，词表会爆炸，而且新词（人名、错别字、代码里的变量名）永远造不完。折中方案就是 **BPE**（Byte Pair Encoding，字节对编码）：从最细的字符出发，统计哪两个相邻片段最常一起出现，就把它合并成一个新 token，反复合并几万到几十万次，直到词表达到预定大小。于是常见词整体成为 token，罕见词被拆成几段，且任何字符串都保证切得开——包括模型从没见过的。

## tokenize 与 detokenize：一次请求的两端

SPOTLITE（本书全部案例来源的 B 站 UP 主，见 [案例出处对照](#/v6/03)）讲 CPU 角色时给过一条完整链路，开头和结尾正是这一对操作：

```text
"你好"          --tokenize（查词表）-->     [108386, 99492]      # id 为示意
[108386, 99492] --detokenize（反查词表）--> "你好"
```

完整顺序是：文本变 token id → 排队调度（细节见 [CPU 在干嘛](#/v3/08)）→ GPU 吞输入与逐 token 吐字（两阶段见 [Prefill 与 Decode](#/v1/07)）→ softmax（把打分变成概率，下一章讲）→ 抽签（行话叫采样）→ detokenize 变回文本。分词和反分词都发生在 **CPU** 上（见 [CPU 在干嘛](#/v3/08)），GPU 只承担中间的重计算。还有一个容易忽略的点：模型输出的不是"北京"两个字，而是"北京"这个 token 的 id——文字只是最后渲染给你看的结果。

> **案例（视频出处：BV1qU846JEpW；BV 号=B 站视频唯一编号）** 一次请求里 CPU 的前期工作就是"对着词表来去分词""把文本变成 token id"，输出端再"根据 token id 进行反 tokenize 转化成文本"。个人场景（只有你一个人在用时）下这些只花几十毫秒；CPU 频率从 1.5G 提到 5G，也只是把几十 ms 压到十几 ms，对整个请求"忽略不计"——分词不是瓶颈，token 的数量本身才是所有账的单位。

## 为什么计费、速度、显存都按 token 数算

**计费**。API 按每百万 token 收费，输入与输出分开计价。你问一句、模型答一段，账单上的 `prompt_tokens`（prompt=你输入给模型的那段话）与 `completion_tokens` 就是两端各自切出来的 token 数，不是字数。顺带一提，"日调用量几万亿 token"这类宣传的分子也是这个计数单位——口径问题见 [口径批判](#/v5/08)。

**速度**。说一张卡跑多少 tok/s，分母就是 token：吐出一个 token 才算一步。同一段话用不同模型切，token 数不同，"每秒能写多少字"自然也不同，读表时的坑见 [先会看表](#/v3/01)。

**显存**（显卡上装模型的那块内存，[显存 vs 内存](#/v4/01) 详解）。推理时的序列长度（sequence length）就是"输入 + 已生成"的 token 总数，而注意力层要为每个历史 token 留一份状态，显存随 token 数线性增长，这笔账叫 [KV 缓存](#/v1/05)；上下文（context）窗口的容量单位同样是 token，见 [上下文窗口与思考预算](#/v1/08)。

> **案例（视频出处：BV1UMEv68E3C）**（这段提前用到后文概念，看不懂可跳过，[v1/05](#/v1/05) 会重算一遍）"满血 256K 上下文"（满血=官方标称的完整规格）的 256K 就是序列长度，约 26 万 token。UP 主拿它去算千问 27B（B=billion，十亿参数；27B=270 亿参数）稠密模型（稠密=所有参数都参与计算，[MoE](#/v1/09) 详解）在 256K 下的 KV 显存（FP16 口径，16 位浮点精度，见 [浮点数从零讲起](#/v2/01)），可这里藏着一笔显存疑账——密码是模型卡里一个叫 Layer type 的字段，[v1/06](#/v1/06) 揭晓。但无论怎么修正，这笔账里"× 序列长度"那一项永远在——token 数就是显存账里会随对话变长而长大的那项。

三个方向共同的根因是：**模型只对 token 做运算**。token 多一步不少算，token 少一步不多算，所以钱、速度、显存全都挂在它身上。

## 怎么验证

验证需要本地模型环境（llama.cpp 或 vLLM，见 [推理框架两流派](#/v3/02)）与一张显卡；没有环境可跳过，不影响后续阅读。

- 查词表大小：打开任一模型的 Hugging Face（全球最大的开源模型托管站）页面，进 `Files and versions` 打开 `config.json`，找 `vocab_size`（十万上下是常态）；同目录 `tokenizer_config.json` 里能看到分词器类型。
- 亲手切一次：

```python
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
print(tok.tokenize("大模型入门"))        # 看中文被切成几段
print(len(tok.encode("大模型入门")))     # 这句话的 token 数
```

- 换一个词表不同的模型（例如 Gemma 系）对同一句话重跑，对比 token 数——你会得到不一样的数字，这就是"token 数依赖具体词表"的直接证据。
- 算显存账：把约 26 万（=256K）代进 [显存三本账](#/v4/02) 的 KV 项，亲手感受长上下文这一项的量级；视频里那笔账错在哪、怎么修正，验证步骤在 [注意力的三个变体](#/v1/06)。
- 对账单：调一次 API，打印返回体里的 `usage` 字段，核对 `prompt_tokens` 是否约等于你输入文本按上面方法数出来的 token 数。
