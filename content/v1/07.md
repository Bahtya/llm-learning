## 一场开卷考试：先读题，再答题

把一次大模型推理想象成开卷考试：你把一整页题目"啪"地拍在它面前，它先把题目从头到尾读一遍——这一步叫 **Prefill**（预填充），也就是视频里形象的"吞字"；然后它一个字一个字往外写答案——这一步叫 **Decode**（解码），"吐字"。两阶段干的事完全不同：

- **Prefill（吞字）**：把你输入的全部 [token](#/v1/01) 一次性并行送进模型，所有位置同时算 [注意力](#/v1/04)，把算出的 K、V 写进 [KV 缓存](#/v1/05)，最后吐出第一个 token。特点：一大口并行算。
- **Decode（吐字）**：[自回归生成](#/v1/02)——一次只算一个 token，读完全部历史，吐一个字，再把它追加进去算下一个。特点：一小口串行吐。

### 快慢差异的本质：并行算 vs 串行吐

Prefill 时几千个 token 齐头并进，矩阵乘得又大又稠密，GPU 的算力单元被全部喂饱；Decode 时每步只有 1 个 token，却要把整份权重从显存搬一遍，算力大量闲置，瓶颈挪到了带宽上（详见[带宽决定 Decode、算力决定 Prefill](#/v4/03)）。所以同一个模型，PP 速度往往是 TG 的几倍到几十倍，具体取决于模型与精度（两个缩写的定义见下一小节）。

### PP/TG：跑分表里的两条腿

llama.cpp 系跑分表通常给两列：**PP**（prompt processing，即 Prefill 吞吐）与 **TG**（text generation，即 Decode 速度）。注意：这是跑分表口径的 PP，与 [双卡怎么放模型：TP vs PP](#/v4/06) 里的流水线并行 PP 是两回事。看任何跑分先分清这两条腿，再确认是不是单并发 batch=1（更细的口径读法见[先会看表](#/v3/01)）。

| 阶段 | 在干嘛 | 指标 | 瓶颈 |
| --- | --- | --- | --- |
| Prefill 吞字 | 输入全体 token 并行前向，填 KV 缓存 | PP / TTFT（首 token 延迟） | 算力 |
| Decode 吐字 | 自回归一次一个 token，读 KV 缓存 | TG | 带宽 |

> **案例（视频出处：BV1YxjU6qEuw）** 单张 2080Ti 跑 27B（Q4_K_M，一种 4 bit 量化档，见 [INT8/INT4 与 GGUF 档位](#/v2/03)），PP 约 580 tok/s；换成两张卡按层切分后 PP 涨到 800 多（+50%），Decode 却不劣化。原理：8K 的 prompt 被切成 4 个 2K 的 batch，单卡必须"40 层全部跑完才轮到下一个 batch"（40 层为视频举例口径，见 [v1/03](#/v1/03)）；双卡 20+20 层流水线接力时，第二张卡算后半段的同时，第一张卡立刻开跑下一个 batch，等于同时在处理约 4K 的 prompt——Prefill 是可重叠的并行计算。而 Decode 是自回归的，"第一个字出完之后才开始跑第二个字"，前后强依赖，重叠不起来。

> **案例（视频出处：BV1qGh56JEj2）** 投机解码实测里的诚实披露：它能加速 Decode，"但他肯定会降低你的 Prefill 的速度"（细节见[投机解码](#/v3/06)）——两阶段不仅不是一回事，还会互相牵制，合在同一个数字里的跑分没有意义。

> **案例（视频出处：BV1otY26LE8w）** 统一内存主机横评里同一模型实测：DGX Spark（统一内存迷你主机，见 [统一内存与 offloading](#/v4/08)）的 Prefill 3000+，AI Max 395（同为统一内存迷你主机）只有 900 多，差好几倍；但两者 Decode 几乎同一量级——因为都是 LPDDR5X（手机与主机常用的低功耗内存）、带宽相近。UP 主总结这类架构"吞字很快，但吐字很慢"。买机器时，这两条腿要分开掂量。

### TTFT：你体感的"快"就是 Prefill

首 token 延迟（TTFT，Time To First Token）= 吞完你全部输入、吐出第一个字的时间。输入越长等得越久，TTFT ≈ 输入 token 数 ÷ PP 速度。聊天时你先感知"开始回话了"，之后才是"每秒出几个字"——前者完全由 Prefill 决定。

> **案例（视频出处：BV1XrE26iEMG）** 8 年老卡 2080Ti 跑 Qwen3.6 27B 稠密模型，INT8 权重（8 位整数，每参数约 1 字节；全量约 30 多 GB）开启"疯狗模式"（作者项目里专拉 Prefill 吞吐的开关）后：纯文本长输入（刘慈欣小说）Prefill 2500 tok/s，长代码输入 2600 tok/s，体感"基本秒回了"；而上一期 FP8（8 bit 浮点格式，见 [FP8 与 NVFP4](#/v2/02)）权重只有 1600–1700 tok/s。注意这次测试关掉了 MTP（多 token 预测，一种投机解码，见[投机解码](#/v3/06)），所以 Decode 并不快——但这不妨碍"秒回"，因为秒回看的是 Prefill。

于是有了那句题眼：**Decode 得快不是真的快，Prefill 快才是真的快。** 长文档问答、贴一大段代码、Agent（智能体，自动多步调用模型的程序，见 [口径批判："调用量世界第一"](#/v5/08)）把工具调用结果整段塞回输入——这些都是几 K 到几十 K token 的大输入，等待时间全由 Prefill 吞吐决定；Decode 再快，也治不了你等第一个字时的焦躁。

### 输入形态也会影响 Prefill

同样的"一页内容"，中文散文和代码切出来的 token 数并不一样，Prefill 时间永远按 token 数计、不按字数计。上面 2500 vs 2600 的对照还有一层意思：好的 Prefill 优化不该只对某种语料生效，纯文本和代码都要快，才算真的快。

## 怎么验证

- **跑一次双指标基准**：llama.cpp 自带 `llama-bench`，`llama-bench -m 模型.gguf -p 8192 -n 128` 会输出 pp 和 tg 两列，分别对应 Prefill/Decode；视频里的实验用的正是 8K 输入。
- **从服务返回里自己算**：llama.cpp server 的返回 JSON 带 `timings` 字段，`prompt_n ÷ prompt_ms × 1000` 就是你的 PP 速度，`predicted_n ÷ predicted_ms × 1000` 就是 TG 速度；vLLM 则看响应里 `usage.prompt_tokens` 配合计时。
- **算一笔 TTFT 账**：拿 BV1YxjU6qEuw 的数字验算——8192 token ÷ 580 ≈ 14 秒（单卡），÷ 800 ≈ 10 秒（双卡）；再按 2600 算：8192 ÷ 2600 ≈ 3.2 秒，"秒回"就是这么来的。把你的真实 prompt 先用 [token 一章](#/v1/01)的 tokenize 方法数出 token 数，就能预测自己的等待时间。
- **做一次输入形态对照**：准备两段长度相近的材料，一段纯小说、一段代码，分别测 PP，看两者的差距与 2500/2600 的结论是否一致。
