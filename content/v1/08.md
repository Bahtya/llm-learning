## 一张桌子的大小：上下文窗口

把模型想成一个只能在一张桌子上干活的助手。这张桌子的面积，就是上下文窗口（context window）：系统提示（开发者预设的角色设定文本）、你贴进来的文档、前面每一轮的问答、模型自己写的思考过程和回答，全部要同时摊在桌上。桌子放不下只有两种后果：要么直接报错，要么最旧的纸被悄悄挪走，这叫截断（truncation），模型从此"看不见"那段历史。

窗口大小按 token 计（[token](#/v1/01)）。"256K 上下文"= 桌上能同时摊约 26 万个 token，粗略说就是一本长篇小说的量。为什么不是无限大？因为[注意力](#/v1/04)要求每个新 token 都回看全部历史：历史越长，每一步要翻的纸越多，显存和算力跟着涨。所以窗口大小是一笔能算出来的成本账，而不只是厂商标签。

### 窗口里都住着谁

一次会话的窗口占用是一条不等式：

```formula
输入 token + 历史轮次 token + 思考 token + 回答 token ≤ 窗口上限
```

| 窗口里的东西 | 谁写进去 | 占不占显存 |
|---|---|---|
| 系统提示 + 你的输入 | 你 | 占 |
| 历史轮次的问答 | 你和模型 | 占 |
| 思考过程（思考预算） | 模型 | 占 |
| 最终回答 | 模型 | 占 |

后两行最容易被忽略：思考与回答也是 token，模型会自己吃掉一块窗口。"我输入才 1K、窗口 256K，所以还剩 255K 随便用"，这笔账是错的。

### 256K 的显存账

窗口里每个 token 都要留一份 [KV 缓存](#/v1/05)（KV cache）；全注意力层（full attention）的 KV 随序列长度线性增长，线性注意力和滑动窗口层则只是固定开销（见[注意力的三个变体](#/v1/06)）。于是上下文开多大，直接决定显存还剩多少给你干活。

> **案例（视频出处：BV1UMEv68E3C）**
> 两张 2080Ti 共 44G 显存，要同时装下千问 27B 稠密模型（AWQ INT4 权重约 20G）和满血 256K FP16 上下文。观众直觉"256K 的 KV 要几十 G 甚至上百 G"，按"64 层全是全注意力"算确实成立：64G，装不下。查模型卡 Layer type 字段发现只有 1/4 的层是全注意力，修正后 256K FP16 的 KV 只要 16G：44G = 20G 权重 + 16G KV + 计算缓冲区，绰绰有余。同一期里 Gemma（60 层中仅 10 层全注意力）也是从 120G 修正到 20G。同样标 256K 的窗口，架构不同，显存代价能差 4~6 倍。

除了显存还有时间账：窗口塞得越满，[Prefill](#/v1/07) 要并行算的 token 就越多，首 token 延迟越长。长上下文从来不免费。

### 思考预算：内心戏也按 token 计价

推理模型（reasoning model）在给出答案前会先写一段思考（thinking）token，思考预算（reasoning budget）就是给这段内心戏设的 token 上限。这些思考 token 是真实成本：同样要走一遍[自回归生成](#/v1/02)（一次吐一个），同样写进 KV 缓存，也要占窗口和时间，走 API 计费时还占钱。

> **案例（视频出处：BV1xQtf6SEHR）**
> 跑 176B 的 Qwen3.8-Flash 时，日常测试把 reasoning budget 掐到 512，让响应快；做深度测试才放宽到 1 万：模型生成"涡轮增压发动机原理动画"花了约 15 分钟、产出约 1.8 万 token，其中相当一部分是思考。同一场实测里上下文开到 160K，用的是 Q4 量化的 KV（[KV 量化](#/v2/06)），窗口大小与 KV 精度同时妥协，才装得下。

上下文窗口是总预算，思考预算是你在预算里的再分配。思考给得越豪爽，窗口里留给"正事"的空间越小，等待也越久。

### 多轮对话：一致性靠窗口续命

多轮迭代是最吃上下文的场景：每一轮的完整历史都得留在桌上，模型才知道"之前说到哪了"。

> **案例（视频出处：BV1nVVr6QEFq）**
> 双 2080Ti 现场让模型生成网页版 FPS 游戏，速度 90 多 tok/s；随后追加需求"增加钓鱼模式"，第二轮仍逼近 100 tok/s（含 MTP 加速；裸 decode：裸=不开任何加速，不开 MTP 约 50 tok/s，带宽理论上限约 60）。第二轮能成立，前提是第一轮生成的全部代码和对话历史还完整躺在窗口里，模型得先"看见"旧代码，才知道往哪儿加。一旦历史超出窗口被截断，模型就开始失忆：改错位置、重复造轮子、忘掉自己之前定过的规则。长上下文能力，最后就看"能不能连续改十轮代码还认得自己的第一版"。

## 怎么验证

- **查窗口**：打开 Hugging Face 模型卡的 config.json，看 `max_position_embeddings` 字段，那就是上下文上限。BV1UMEv68E3C 里查的 `Hidden layer`（层数）与 `Layer type`（层类型）也在同一张卡上。
- **算 KV**：代入 [KV 缓存](#/v1/05)的公式 `层数 × KV头数 × head_dim × 2 × 序列长度 × 每元素字节数`，但先看 Layer type 确认全注意力层占比：千问 27B、256K、FP16、1/4 全注意力，应得约 16G；要是算出 64G，说明你把 64 层全当成全注意力了。
- **数 token**：把 prompt 丢进 tokenizer（模型卡页面右侧的测试框，或 `tiktoken`/`transformers`），核对"输入 + 历史 + 预留思考 + 预留回答"有没有顶到上限。
- **看时间账**：llama.cpp 日志的 `print_timings` 会分别给出 prompt eval time（Prefill）和 eval time（Decode）。故意把上下文从 4K 拉长，对比首 token 时间的变化。
- **掐思考**：同一个问题，分别把 reasoning budget 设为 512 和 1 万，比较总耗时与产出 token 数，你会亲眼看到内心戏的价格。
- **测失忆**：复现"生成网页游戏 → 加钓鱼模式"的两轮流程；然后故意删掉第一轮历史再发第二轮，观察模型是不是开始瞎改。
