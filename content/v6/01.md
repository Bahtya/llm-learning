## 七个方法论模式：一套可以抄的作业

追完前五卷你会发现，这些视频的结论长得很像：先质疑一个流行说法，再打开一手资料，列公式算账，上机实测，最后把一切扔进开源仓库让别人复现。这背后是一条固定流水线。本章把它拆成七个模式，每个配一个视频实例；以后再刷到"XX 吊打 XX""调用量世界第一"，按这七步过一遍即可。

用 debug（排查程序哪里出了毛病的全过程）打比方：复现问题（现象）→ 读源码而不是读二手博客（一手字段）→ 对半排查（控制变量）→ 上 profiler（给程序逐项记时间账的工具）看真实开销（算账实测）→ 写进回归测试（改完代码后重跑旧用例确认没改坏；对应开源复现）。你早就会这套流程，只是还没把它用在"买卡、跑模型、看榜单"上。

```text
现象/质疑 → 查一手资料 → 列公式算账 → 上机实测 → 公开复现
```

### 模式一：先算账再动手

大额决策前先列公式估算，连公式本身也要审："这公式对的吗？"算账花十分钟，省掉的是几千元试错和几周等待。显存三本账（权重 + KV 缓存（KV cache）+ 计算缓冲区，见 [显存三本账](#/v4/02)）、电费账、24 小时 token 产出账，都是这一模式的产物。

> **案例（视频出处：BV1UMEv68E3C）**
> 面对"两张 2080Ti 共 44G 怎么装得下 256K FP16 上下文"的质疑，UP 主先按通行 KV 公式算出 64G（千问 27B）与 120G（Gemma），再回头审公式，修正后只有 16G 与 20G。最终 44G = 20G 权重 + 16G KV + 计算缓冲区，"绰绰有余"。

### 模式二：信一手字段，不信二手结论

翻案靠的不是更权威的博主，而是模型卡里的一个具体字段。别人断言"不可能装得下"，他打开 Hugging Face 模型页，把字段一层层数给你看（KV 显存公式见 [KV 缓存](#/v1/05)，注意力变体见 [注意力的三个变体](#/v1/06)）。

> **案例（视频出处：BV1UMEv68E3C）**
> Layer type 字段显示：千问 27B 的 64 层里只有 1/4 是 full attention，其余 3/4 是带 GDN 缓存的 linear attention；Gemma 60 层只有 10 层全注意力、50 层是窗口 1024 的滑窗。64G 缩到 16G、120G 缩到 20G，凭的就是这一个字段（完整翻案见 [KV 缓存 100G 算账翻案](#/v5/02)）。

### 模式三：控制变量实验

一次只动一个变量：同模型、同量化、同 prompt，只换要考察的那一项；报数字时还要标注"最高速度不等于稳定复现速度"（口径见 [先会看表](#/v3/01)）。反过来，各跑各的配置、只挑好看的数字互相攀比，圈内自嘲为"赛博斗蛐蛐"，热闹归热闹，说明不了任何问题。

> **案例（视频出处：BV1dx3Q6iEbZ）**
> 验证"没有 NVLink，多卡还能不能加速"：三组相同卡做对比组，固定 4K prompt + 2K ubatch，只改并行方式。双卡流水线并行（Pipeline Parallelism）下 Prefill：170HX +72%、MI250 +60%、2080 +50%，Decode 全部不劣化，连 PCIe 1.0 x4 的矿卡飞线环境都不例外。

> **案例（视频出处：BV1Y2LX61EjQ）**
> 同一套实测里的诚实标注："这是最高速度，不一定是可以稳定复现的速度"；没实测过的组合明确写成"推测值，没有实际验证过"。

### 模式四：口径批判

看到"第一/最强"先问统计口径：样本是谁、窗口多长、单位是什么。这里最常见的坑是抽样偏差（sampling bias）：你手里的数据只是一部分样本（比如某个平台的周榜），却把它当成了全体用户的行为；样本从哪来，结论就只对哪儿成立。最快的武器是除法：用大数除以小数，反推数量级是否合理（整章案例见 [口径批判](#/v5/08)）。

> **案例（视频出处：BV1kgN26SECZ）**
> "某模型 OpenRouter 周调用量世界第一"：周榜约 6.13 万亿 token，重度 API 用户一周约用 140~150 亿。6.13 万亿 ÷ 150 亿 ≈ 400 人。只需 400 个重度用户就能刷上周榜第一，而主流模型用户量级是几百万，差着 4 个数量级。

### 模式五：成本工程

一切换算成价格锚点：每 TFLOPS 多少钱、每 64G 内存多少钱、每百万 token 多少钱；总账（总拥有成本，完整账法见 [紧急刹车：本地 vs API 的 TCO](#/v5/07)）= 购置 + 电费 + 精力 + 风险。

> **案例（视频出处：BV1KKE96CELt）**
> 满载上限账：100 tok/s（含 MTP 加速）× 3600 秒 × 24 小时 ≈ 864 万 token/天，电费"十几到 20 块"。而每百万输出 2 元的 API，20 元能买 1000 万 token，比本地一天的极限产出还多。"我们用了一个更贵的价格，去用一个更弱的模型"，硬件与矿卡风险还没算进去。

### 模式六：以终为始

先定工作负载（个人单并发？Agent？AIGC（AI-Generated Content）？），再反推硬件；"能不能跑"先于"跑得快不快"。

> **案例（视频出处：BV14UEY6WEW7）**
> Pro6000（96G）半年从 6 万炒到 10 万。做 AIGC 它是王炸；跑本地 LLM 却两头不靠：开源模型已分化成 30B 档（民用卡塞得下）与 200B 档（多是 MoE（Mixture of Experts），每步只激活 10B，即 A10B 这一档），96G 卡在中间。结论："要以终为始，不要盲目的消费。"（30B 甜点位见 [模型生态与幻觉](#/v1/10)，MoE 见 [MoE：总参数与激活参数](#/v1/09)）

### 模式七：开源复现 + 社区校验

结论要写进仓库：测试配置、权重清单、版本号全部公开，让同型号机器能对答案（案例通读见 [双 2080Ti 27B 100tok/s 全拆解](#/v5/01)）。

> **案例（视频出处：BV1xQtf6SEHR）**
> 把 176B 模型塞进两张 400 元老卡加 100 元 U盘那期，测速工具 LLMSPEEDCHAT 直接开源；Prefill 314 token/s 这个数从 llama.cpp 日志里读出来给你看。数字可核查，比"秒天秒地"的截图值钱。同一项目从 0.1.4 迭代到 0.1.6，每期都报版本号，别人拿到同一个 commit 就能复现。

### 把这套方法用在你自己的学习上

- **抄公式、代自己的数**：看到任何公式（KV 显存、电费、产出），换上你的上下文长度、电价、卡，重算一遍，数量级感就有了。
- **下沉到字段**：`config.json` 里的 `num_hidden_layers`、`num_key_value_heads`、`head_dim`、Layer type，比任何评测都硬。
- **一次只改一个变量**：换权重精度就别同时换框架，否则你不知道收益归谁。
- **先问口径，再问可复现性**：给不出配置和版本号的跑分，按零分处理。

## 怎么验证

- **复算那笔 16G**：16 个全注意力层 ×（KV头数 × head_dim = 1024）× 2（K 与 V）× 262144（256K）× 2 字节（FP16）= 16 GiB。打开模型页 `config.json` 核对字段，再数一遍 Layer type 里 full attention 的行数。
- **复算刷榜账**：6.13e12 ÷ 1.5e10 ≈ 409 人。
- **复算电费账**：100 × 3600 × 24 = 8,640,000 token/天；20 元 ÷ 2 元/百万 = 1000 万 token，比一比谁大。
- **做一次对照实验**：同模型同 prompt，只关 MTP 重跑一次，分别记录 Prefill 与 Decode（日志字段见 [Prefill 与 Decode](#/v1/07)），验证"前者几乎不动、后者明显下跌"。
- **查仓库而不是查人**：star 数之外看版本号、commit 与 issue 记录，持续在修 bug 的仓库，结论才值得押注。
