## 模型放不下：先拼接显存，再决定怎么切

[Q4 量化](#/v2/03)后的 27B 模型约 16.5G（Q4_K_M 口径，见 [显存三本账](#/v4/02) 的 27B 权重对照表），一张 16G 卡怎么都塞不下。把两张卡的显存拼成一个池子（显存拼接），模型切成两半各住一边，"能不能跑"就解决了。但切法决定速度：一本书两个人抄，可以按章节分，你抄前半本、我抄后半本，中途交一次货；也可以把每一页撕成两半，每页两人各抄半页，每页都对一次答案。前者是流水线并行（pipeline parallelism，PP；注意：这个 PP 与 v1/07 跑分表的 PP=prompt processing 是另一个 PP），后者是张量并行（tensor parallelism，TP）。

### PP：按层接力，中途只交一次货

[权重按层堆放](#/v1/03)，40 层模型左边放 20 层、右边放 20 层，1:1 对半切。这个 40 层是视频随手设的举例口径，本章 TP 案例里千问 3.6 27B 实际是 64 层。数据像流水线上的工件：第一张卡算完自己的 20 层，把分界层的 hidden state（隐藏层状态）递给第二张卡，llama.cpp 里这叫 layer split。

通信量一条公式：`payload = hidden_size × token 数 × 每元素字节数`（payload＝单次传输量）。按 [2K 的 micro-batch](#/v3/04)、hidden_size 5120、FP16 每元素 2 字节算，一次交接约 20MB；decode 时 token 数是 1，payload 掉到 10KB，"小得基本可以无视"。

prefill 为什么能快？[Prefill 的 token 可以并行](#/v1/07)：8K prompt 拆成 4 个 2K batch，第一张卡把第 1 个 batch 的前 20 层算完递出去，立刻回头算第 2 个 batch，两卡的计算时间重叠。decode 做不到：[自回归](#/v1/02)的下一个 token 必须等前 20 层、后 20 层全部算完才能开始，手里没有第二个 batch 可以填空。所以 PP 对 decode 不提速、也不减速。

> **案例（视频出处：BV1dx3Q6iEbZ）** 三组同卡对照：矿卡 170HX 飞线（手工焊线补电路，见 v4/10）改装后只剩 PCIe 1.0 x4（卡槽总线，见 v4/07），双卡 layer split 的 prefill 仍比单卡快约 72%；MI250（AMD 下一代数据中心卡）快 60%，2080 快 50%，decode 均不劣化。16.5G 的 Q4 模型放进两张 16G，速度不输一张 32G。"没有 NVLink、没有点对点直连（P2P，peer-to-peer，卡间直连）、没有大带宽，多卡照样能加速"，前提是走 PP。

### TP：每层切开，每层都对一次答案

TP 把单层内部的权重切成两半，两卡同时算这一层，再靠全局规约（all-reduce）把两份半成品合并成完整结果。代价是每一层都要合并：约 64 层的模型（下方案例的千问 3.6 27B）每层 2 次，一次前向固定约 129 次（多出的 1 次来自输出层）。拆法说明：视频口播只报了"每层都要归并、一次前向约 129 次"的总数，"每层 2 次"是本书按 129÷64 反推的均分口径。prompt 变长不会增加合并次数，变的只是单次 payload。通信总量 = payload × 次数：prefill 变大的是单次传输量，decode 变多的是传输次数。

> **案例（视频出处：BV1Y2LX61EjQ）** 千问 3.6 27B 双卡 TP 的性能剖析（profiler）统计：4K prompt 的 Prefill 逻辑发送总量 5G 多、合并 129 次；prompt 加到 64K，总量暴涨到约 80G，合并次数仍是 129 次，变大的是单次 payload。反过来看 Decode：吐 128 个 token 总量只有 161MB，却合并了 1.6 万多次；吐 1000 个 token 总量 1.26G，合并约 13 万次，变多的是次数。

于是两个阶段挑的东西不同。Prefill 的 payload 动辄几十 MB，搬运时间看卡间带宽（bandwidth），带宽越大损耗越小，所以 prefill 带宽敏感。Decode 每次只有 10KB，搬起来不费时间，但每次通信都带一份固定开销（发起、同步、握手），129 份固定开销要挤进吐一个 token 的几十毫秒里，所以 decode 延迟敏感（latency）。

> **案例（视频出处：BV1Y2LX61EjQ）** 拓扑（卡和 CPU 之间怎么连）降级实测：服务器平台双 x16 直连 CPU 时，Decode 与 NVLink 基准几乎一致；换成家用主板把 x16 拆成两个 x8（同一 root 下仍可 P2P；root=这些通道的源头，下章讲），Decode 只掉 3%~5%，Prefill 却明显变慢。decode 不挑带宽，prefill 挑。同一项目的 2×2080Ti 22G + NVLink 桥接基准：Prefill 1700 tok/s、Decode 50，[开 MTP](#/v3/06) 后翻到 100。

### decode 想快，只有 TP 这条路

PP 的接力在 decode 里重叠不起来；TP 却正打在 decode 的痛点上：decode 是[访存受限](#/v4/03)的，每吐一个 token 要把权重完整读一遍；两卡各存一半权重，每张卡只读一半，等效显存带宽翻倍，decode 理想情况能翻倍（实际达不到理想值，拓扑尚可时一定快过单卡）。代价是每层都通信，对卡间互联挑三拣四，这正是 [NVLink](#/v4/07) 的用武之地；PP 全程只交几 MB 的货，PCIe 1.0 x4 都无所谓。

| | 流水线并行 PP | 张量并行 TP |
| --- | --- | --- |
| 切法 | 按层 20+20 | 单层内部对半 |
| 卡间通信 | 每个 micro-batch 一次 hidden state | 每层 all-reduce，约 129 次/前向 |
| 单次 payload | prefill 约 20MB / decode 10KB | prefill 几十 MB / decode 10KB |
| Prefill | 重叠加速（+50%~72%） | 提速但吃带宽 |
| Decode | 不提速不减速 | 等效带宽翻倍 |
| 对互联的要求 | 几乎不挑 | 挑带宽，更挑延迟 |

## 怎么验证

- **复算 payload**：打开模型目录的 `config.json`，读 `hidden_size`（27B 级约 5120）和 `num_hidden_layers`（约 64）。单次 all-reduce = hidden_size × token 数 × 2（FP16）。套视频数字：4096 × 5120 × 2 ≈ 42MB，× 129 ≈ 5.4GB，对上"5G 多"；65536 个 token 时约 87GB，对上"暴涨到 80G"（量级一致，精确值以 profiler 为准）。
- **复算合并次数**：129 ≈ 每层 2 次 × 64 层 + 1（多的 1 次来自输出层）。拿它乘 token 数：128 × 129 ≈ 1.65 万、1000 × 129 ≈ 12.9 万，对上"1.6 万多次"和"13 万次"。公式对得上，数字才可信。
- **跑一次双卡对照**：llama.cpp 用 `llama-bench -m 模型.gguf -sm layer -ts 1,1`（layer split），再换 `-sm row`（层内切，即 TP）对比 PP/TG 两列；vLLM 对应 `--pipeline-parallel-size 2` 与 `--tensor-parallel-size 2`。
- **验证敏感度差异**：固定模型，把卡间链路从 NVLink 换成普通 PCIe，跑一遍 decode 延迟敏感、prefill 带宽敏感的实验版：TG 几乎不动、PP 掉一截。
