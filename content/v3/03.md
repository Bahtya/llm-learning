## 引擎不是发动机，是管家

最朴素的推理是二十行 PyTorch（最常用的 AI 编程库）：读权重、循环前向、取下一个 token。这个循环只会"算"——不知道请求从哪来、不会排队、更不会管越用越大的 KV 缓存（[KV 缓存](#/v1/05)）。**推理引擎（inference engine）**干的正是这些脏活：收请求、排队、切批、管显存、流式吐字。上一章说过 llama.cpp 与 vLLM 分属两派（[推理框架两流派](#/v3/02)），vLLM 作为服务级代表，核心武器只有一个：PagedAttention（分页注意力）。

## KV 空间是怎么被浪费的

KV 缓存显存随序列长度线性增长：层数 × KV 头数 × head_dim × 2 × 序列长度 × 每数字节数（账目见 [显存三本账](#/v4/02)）。麻烦在于框架必须在请求一开始就决定留多大空间，朴素做法是按上限预留一整块连续显存：上下文开多大，预留多大。

算一笔账：8B 级 GQA 模型（32 层、8 个 KV 头、head_dim 128、FP16）每 token KV 约 128 KB，上限开 32K 就是一个请求预留 4 GB；而多数回复只生成几百到几千 token，实际用上的不到一成。剩下九成显存空着，别的请求还插不进来，这叫**内部碎片（internal fragmentation）**。vLLM 论文实测过，这类做法的 KV 有效利用率只剩两到四成，同卡并发容量跟着只剩两到四成。

## PagedAttention：跟操作系统学分页

操作系统几十年前就解过同类问题：进程眼里地址连续，物理内存按页散落，靠页表翻译。PagedAttention 把这套思路搬到 KV 上：

- **逻辑块（logical block）**：每个序列的 KV 在逻辑上仍是一串连续的块；
- **物理块（physical block）**：真实显存切成固定大小的块（block size，vLLM 默认 16 个 token 一块），哪里有空放哪里；
- **块表（block table）**：记录逻辑块号到物理块号的映射，注意力计算按表寻址。

收益三条：碎片上限从"整段预留"缩到"最多一个块"，浪费降到 4% 以内；KV 按需生长，要多少给多少；省下的显存装进更多并发请求的 KV——单请求速度没变，总吞吐成倍上去（口径见 [tok/s、吞吐与单并发](#/v3/01)）。多个请求共享同一段前缀时还能直接指向同一批物理块，这就是 vLLM 前缀缓存（prefix caching）的地基。

## 请求进来之后：排队与调度

一次请求的完整链路，就是引擎的主循环：

- HTTP Server 收请求；
- 分词（tokenize）把文本变成 token id（[token、词表与 BPE](#/v1/01)）；
- 排队调度：决定谁先上、切块（chunk）切多大；
- GPU 先 prefill 吞下提示词，再逐 token decode（[Prefill 与 Decode](#/v1/07)）；
- 反分词（detokenize）转回文本返回。

vLLM 内部有 waiting 与 running 两个队列：有空闲物理块才放行进 running；块耗尽时宁可抢占（preemption）——把请求踢回 waiting，重算或换出它的 KV，也不让显存爆掉。每个并发请求各有一条逻辑块链，批怎么切见 [并发与批处理](#/v3/04)；vLLM 每张卡还对应一个 TP worker（TP=张量并行，见[双卡怎么放模型](#/v4/06)）进程，worker 与 CPU 各自管什么，见 [CPU 在干嘛](#/v3/08)。

### 数字锚点

> **案例（视频出处：BV1nVVr6QEFq）** 两张 2080Ti 加 NVLink 桥、配 500 元主机，整套约 4500 元跑 Qwen 27B 稠密模型，引擎是魔改的 vLLM（项目名 vLLM-2080Ti-Definitive）。现场生成网页版 FPS 游戏，单并发 decode 实测 80~100 tok/s（含 MTP 加速；同一套卡裸 decode 约 50，见 [先会看表](#/v3/01)）；追加需求"加个钓鱼模式"继续迭代，仍在 90 多、逼近 100。参照系是一张约 5 万元的 RTX PRO 6000："可能也就是这个速度"。老卡追平专业卡的单并发体验，另一半功劳就在引擎层的显存管理与调度。

> **案例（视频出处：BV1qU846JEpW）** 同一条链路里 CPU 只承担分词加排队调度，低并发下合计"几十毫秒甚至更低"；频率从 1.5 GHz 提到 5 GHz（约 3 倍）也只压到十几毫秒，对秒级的整段请求"忽略不计"。重负载的 prefill、decode、多卡通信全在 GPU 上——引擎排队的全部意义，就是别让 GPU 闲着，也别让 KV 池溢出。

## 怎么验证

1. 起服务：`pip install vllm` 后 `vllm serve Qwen/Qwen2.5-7B-Instruct`。
2. 看启动日志 `# GPU blocks: NNN`，乘上默认块大小 16 就是 KV 池能装的 token 总数；新版日志还会给 `Maximum concurrency`。
3. 把 `--max-model-len` 从 32768 降到 8192 重启：`# GPU blocks` 几乎不变（池子=剩余显存全给 KV，不按单请求上限预留），变的只是单请求逻辑块链能拉多长。
4. 读实现：源码搜 `block_table`、`BlockSpaceManager`（新版 `KVCacheManager`），`--block-size` 可改 8/16/32。
5. 压测：仓库自带 `benchmark_serving.py`，同卡分别测 batch=1 与 32 并发，验证"单请求速度被摊薄、总吞吐放大"。
