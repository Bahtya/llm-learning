## CPU 在干嘛：不止是个观众

跑推理时打开任务管理器：总有一两个核心（core）钉在 100%，其余核心很闲。很多人由此得出"换个强 CPU，推理更快"。这章就拆这个误会。类比是餐厅：GPU 是后厨，CPU 是前台服务员——接单（收请求）、把菜单翻成后厨看得懂的单据（分词）、决定哪几桌并一锅炒（调度）、上菜（返回文本）。服务员确实一直在小跑，但菜炒得快不快，跟他跑多快关系不大。

### 一次请求的完整旅程

纯 GPU 推理（权重全部装进显存，见 [显存 vs 内存](#/v4/01)）时，一次请求走这条流水线：

- **HTTP 服务器（HTTP server）**收到请求——你本地跑的模型其实是个网络服务，按请求-响应（request-response）模式干活；
- **分词（tokenize）**：文本对着词表变成 token id（见 [token、词表与 BPE](#/v1/01)）；
- **排队调度（scheduling）**：请求何时进队、按 chunk 与 micro-batch 怎么分组、各配多少 KV 空间（见 [vLLM 与 PagedAttention](#/v3/03)、[并发与批处理](#/v3/04)）；
- **Prefill 与逐 token Decode**：重头戏，全在 GPU（见 [Prefill 与 Decode](#/v1/07)）；
- **softmax 出概率分布、采样**出下一个 token（见 [生成 = 预测下一个 token](#/v1/02)），再 **detokenize（反分词）**把 token id 变回文本；
- HTTP 服务器把文本装进响应发回去。

分词/反分词这类字符串活加上排队调度，在 CPU；Prefill、Decode 这些重负载在 GPU。即使用张量并行（tensor parallelism，TP，见 [双卡怎么放模型](#/v4/06)）把模型切开，卡间通信的重负载也仍在 GPU 侧。

> **案例（视频出处：BV1qU846JEpW）**
> UP 主拆完整链路：HTTP Server 收请求 → 对词表分词变 token id → 排队调度、按 chunk/micro-batch 分配 KV cache → prefill 填充 → 逐 token decode → softmax 得分（temperature=0 的贪心采样直接取最高概率那个）→ 反 tokenize 转回文本 → 返回。"前期这两步是 CPU 他要做的事情……真正的填充跟吐字的这个阶段，这时候就是我们的这个 GPU 要发挥作用。"

### 几十毫秒 vs 几秒钟：算占比

低并发（concurrency）下，CPU 的前期工作只要几十 ms 量级。生成阶段呢？单并发 100 tok/s（含 MTP 加速）吐 500 token 要 5 秒——CPU 那几十 ms 只占约 1%，用户毫无感知。这就是单核性能、IPC（instructions per cycle，每周期指令数）、频率"何时重要"的答案：纯 GPU 推理、个人低并发时几乎不重要；例外是模型本体跑在 CPU/内存上，那时 CPU 自己就是算力（见 [统一内存与 offloading](#/v4/08)）。

> **案例（视频出处：BV1qU846JEpW）**
> UP 主的原话账："前期的处理时间，可能也就只有个几十 ms 甚至更低"；把 CPU 频率"从一个 1.5G 提升到 5G"，提升约 3 倍，也只是"把整个几十 ms 的时间，拉低成为十几毫秒，它对于我们整个请求来说可以说是忽略不计"。所以个人低并发场景，"CPU 的影响真的不大"。

> **案例（视频出处：BV12ZEN6CEho）**
> 双卡 3500 元（整套约 4500，见 [一张 4500 元的账单](#/v5/01)）的双 2080Ti 22G 方案，主机是联想 M720q Tiny，CPU 是 i3-9100T，只有 4 核 4 线程、35W TDP。TDP 是散热设计参考值，不是电表读数（见 [平台与功耗](#/v4/09)）；UP 主反讽"功耗高达 35 瓦，性能非常强劲"——反话，35W 其实很低。内存配双通道 2×8G DDR4 2400MHz，两条内存一起用、带宽翻倍；内存不能省，是为了装得下模型（见 [显存 vs 内存](#/v4/01)）。这套"弱 CPU"照样跑出 27B 稠密（dense）模型 100+ tok/s（含 MTP）——瓶颈在卡，CPU 够用就行。

### 高并发时，CPU 重新上台

请求数与 batch 变多后，分词、组批、调度的工作量随请求数线性上涨，CPU 侧才可能成为瓶颈。所以结论要分两半说：**单核性能不重要；多核性能与多核调度才重要**——商业部署对此敏感，个人低并发无所谓。攒机时预算的大头仍应留给显卡；个人场景反正只看单并发（见 [先会看表](#/v3/01)），更不必为 CPU 多花钱。

### TP worker：每张卡一个分片进程

vLLM 这类服务级框架（见 [推理框架两流派](#/v3/02)）在 TP 模式下，每张卡对应一个 **TP worker** 进程：进程内持有 1/N 份权重分片、在自己那张卡上执行前向计算；CPU 侧只承担协调与调度，开销小。UP 主口播说 worker"只调度、不运算"，那是从 CPU 视角说的，别误成 worker 不碰计算。

> **案例（视频出处：BV1qU846JEpW）**
> "特别像 vLLM，它会多一个叫 TP worker……他这 worker 就是进行双卡的调度，但不是进行双卡的运算。"（口播从 CPU 视角描述；worker 进程本身在各自那张卡上跑 1/N 分片的前向计算。）所以"卡越多，活跃的这些核心会越多"——看到一两个核心满载属正常现象，那是协调与分词线程，不等于 CPU 拖了后腿。

## 怎么验证

- **看核心**：跑推理时开 `htop`（Windows 用任务管理器切到"性能"），应看到一两个核心接近 100%、其余空闲。这是调度/分词线程，不是瓶颈信号。
- **拆时延**：对本地服务（llama.cpp 的 `llama-server` 默认 8080，vLLM 默认 8000）发一条流式请求并用 `curl -w` 计时：

```bash
curl -s -o /dev/null -w "连接 %{time_connect}s 首token %{time_starttransfer}s 总计 %{time_total}s\n" \
  http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"m","messages":[{"role":"user","content":"写一首七绝"}],"max_tokens":500}'
```

`time_starttransfer` ≈ 连接+排队+分词+prefill+首 token；`time_total` 减去它就是纯 decode 时间。CPU 前期工作藏在首 token 之前那一小段，对照总时长算占比。
- **数 worker**：vLLM 用 `--tensor-parallel-size 2` 启动后，`ps -ef | grep vllm` 里应有 2 个 worker 进程（=卡数）；`nvidia-smi` 也能看到每张卡各挂一个进程。
- **算一笔账**：500 token 回复、100 tok/s → decode 约 5 秒；CPU 前期按 50 ms 算占 1%。频率翻 3 倍最多省 30 多 ms，感知为零。再看 i3-9100T 那套机器的 100+ tok/s：两组数字互相印证——个人推理的预算，显卡说了算。
