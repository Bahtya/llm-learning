## 同一个 tok/s，两种完全不同的口径

把推理服务想成一个食堂窗口。**吞吐量（throughput）**是这个窗口一小时总共打出去多少份饭，同时排二十个人时总数相当可观；**单并发输出速度**是你一个人坐在餐桌上、每秒实际吃进几口。两个数字的单位都叫"份/秒"，含义却天差地别。

大模型的 tok/s（tokens per second，每秒 token 数）同样分两种口径：

- **吞吐（throughput）**：服务端同时处理很多请求，把所有请求每秒产出的 [token](#/v1/01) 数加总。数字最大，但那是几十个用户分掉的。
- **单并发输出速度**：只有你一个请求（batch=1）时，模型每秒吐给你的 token 数。数字最小，但每一个 token 都是你的。

粗略换算：吞吐 ≈ 单并发速度 × 并发数。并发越多，单个请求分到的越少、总量却越高，服务端跑分也就爱用高并发把吞吐刷漂亮；排队与切批的细节在[并发与批处理](#/v3/04)展开。

| 口径 | 数字长相 | 回答的问题 |
| --- | --- | --- |
| 吞吐 | 大，随并发数上涨 | 这台机器一小时能服务多少人 |
| 单并发 batch=1 | 小，独占全部资源 | 我一个人用起来有多快 |

> **数字精度声明**：文中百分比按视频口播四舍五入，复算误差 ±10% 内，重点在口径与量级，不在末位数字。

### 个人用户只该认 batch=1

你是唯一用户：没有排队，没有和别人摊薄，模型把整份带宽都交给你。这是本地部署最真实、也最容易被跑分表藏起来的一项。

> **案例（视频出处：BV1nVVr6QEFq）** 两张 2080Ti + NVLink（卡间直连桥，见 [NVLink 与 PCIe 全家桶](#/v4/07)）+ 500 元主机，整套 4500 元跑 27B 稠密模型，现场读速"90 多了""接近 100"tok/s（含 MTP）；边生成网页 FPS 游戏、边按新需求加钓鱼模式，速度仍在 90 多。关键在口径干净：这是单并发 Decode 输出速度，没有任何并发摊薄。UP 主拿它对比约 5 万元的 RTX PRO 6000"可能也就是这个速度"，两者比的也是同一口径，数字才有可比性。

反过来，若宣传只说"跑到 3000 tok/s"却不提并发数，多半是吞吐口径：二十个用户摊下来，每人只剩 150。

### PP/TG：跑分表两列各说各的故事

llama.cpp 系跑分表给两列：**PP**（prompt processing）即 [Prefill 与 Decode](#/v1/07) 里的 Prefill 吞吐，**TG**（text generation）即 Decode 输出速度（通常 batch=1）。两阶段快慢本就差十几倍，所以"PP 1700、TG 50"不是作假，是常态。

> **案例（视频出处：BV1YxjU6qEuw）** 同一张表里，PP 与 TG 可以完全不同步：MI50（AMD 老数据中心卡，见 [显卡天梯](#/v5/04)）16G 单卡跑 35B 级模型 PP 600 多，换两张 16G 各分一半层（见 [双卡怎么放模型：TP vs PP](#/v4/06)）后涨到 1000 多（+60%）；2080Ti 跑 27B Q4_K_M 单卡 PP 580 → 双卡 800 多（+50%）。而两边的 Decode 都不劣化、也不加速。只看一个笼统的"快了多少"，这组实验就读不出结论：同一 8K 的 prompt 拆成 4 个 2K batch，双卡按层接力让它们重叠跑，Decode 是[自回归](#/v1/02)的、前后层强依赖、重叠不起来。两阶段瓶颈为何不同，见[带宽决定 Decode、算力决定 Prefill](#/v4/03)。

### 最高速度 ≠ 稳定复现速度

> **案例（视频出处：BV1Y2LX61EjQ）** 同一项目的实测 baseline（基准线）：双卡 NVLink 直连，Prefill 1700 token/s，Decode 不开 MTP 约 50、开 MTP 为 100（MTP=多 token 预测，一种投机解码）。报完数字 UP 主立刻补了一句："这是最高速度，不一定是可以稳定复现的速度。"（MTP 为何能让 Decode 翻倍，见[投机解码](#/v3/06)。）

基准工具报出来的常常是多次采样里最好的一次。系统调度、后台进程、温度降频、缓存是冷是热（数据在不在快的地方），都会让同一条命令的读数上下浮动。所以看任何速度数字先问三件事：哪个口径（PP 还是 TG）、几路并发、峰值还是均值；自己汇报成绩时也把这三个前提写全，数字才有公信力。

▶ 插画：并发越高总吞吐越涨、你自己那路越慢。

## 怎么验证

- **跑一次双列基准**：`llama-bench -m 模型.gguf -p 4096 -n 256 -r 5`，输出表里 pp 与 tg 各成一列、各带 ± 误差，`-r` 控制重复次数，口径与波动这两个问题一条命令同时回答。
- **做一个并发对照实验**：用 `llama-server` 起服务后，先发一条请求记下基准，再用两条 curl 同时发：

```bash
curl -s http://127.0.0.1:8080/completion \
  -d '{"prompt":"写一首长诗","n_predict":256}' &
curl -s http://127.0.0.1:8080/completion \
  -d '{"prompt":"写一篇散文","n_predict":256}' &
wait
```

  对比两条返回里的 `timings.predicted_ms`：每个请求的速度几乎腰斩，两条加起来的总吞吐却接近翻倍。Decode 阶段并发能近似翻倍总吞吐，Prefill 阶段则两路互相摊薄（组批细节见[并发与批处理](#/v3/04)）。亲眼见过"单请求减半、总吞吐翻倍"，两种口径就再也不会混。
- **算一笔等待账**：4096 token 输入 ÷ PP 1700 ≈ 2.4 秒出首字；600 token 的回答 ÷ TG 50 ≈ 12 秒写完，同卡开 MTP 到 100 则只要 6 秒；换成双 2080Ti 那套 100 tok/s（含 MTP），600 token 也只要 6 秒。一段文字切多少 token，按[token、词表与 BPE](#/v1/01)的方法先数一遍。
- **复核别人的数字**：找到原始表格后核对三前提（口径、并发数、峰值/均值），缺任何一项，就把那个数字降权处理。
