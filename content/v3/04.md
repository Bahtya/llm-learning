## 并发与批处理

Decode（吐字）阶段每生成一个 token，都要把整套权重从头读一遍（见 [带宽决定 Decode、算力决定 Prefill](#/v4/03)）。这像开班车过收费站：过路费按车次收，坐一个乘客和坐满一车人，成本几乎一样。既然车总要开，就让多路请求拼同一辆车，也就是**批处理（batching）**：把多个 token 排成矩阵，一次前向（forward）一起算，一趟车多装货。所以 batch 是推理引擎抬升吞吐（throughput）的第一杠杆。

### 三个词：并发、batch、ubatch

- **并发（concurrency）**：同时服务中的请求数。单并发即 batch=1，是个人使用最真实的速度口径（见 [先会看表](#/v3/01)）。
- **batch（批）**：一次前向里并排计算的 token 集合，既可以由不同请求拼成，也可以是一条长 prompt 切出来的段。
- **micro-batch / ubatch**：逻辑 batch 再切小的物理计算单元，llama.cpp 叫 ubatch（参数 `-ub`/`n_ubatch`）。长 prompt 不是一口气灌进模型，而是按这个粒度分块过层。

> **案例（视频出处：BV1qU846JEpW）**
> UP 主拆一次请求的完整链路：HTTP Server 收请求 → 分词变 token id → **排队调度：按 chunk/micro-batch 把 token 分进 batch、各自对应一份 KV cache** → prefill → 逐 token decode。分词与组批都是 CPU 的活，个人低并发下只花"几十 ms 甚至更低"；CPU 频率从 1.5G 提到 5G（约 3 倍）也只省十几 ms，"忽略不计"。高并发、batch 与请求都变多之后，CPU 侧调度才可能成为瓶颈（见 [CPU 在干嘛](#/v3/08)）。

### 每路并发，都有自己的一本 KV 账

批处理省的是算力和搬权重的时间，**不省 KV 显存**：每条请求的上下文不同，注意力各看各的历史（见 [KV 缓存](#/v1/05)），每路并发都要一份独立的 KV 空间。显存三本账（见 [显存三本账](#/v4/02)）里权重只有一份，KV 那本却要乘上并发数，**8 路并发就是 8 倍 KV**（共享前缀除外，见 [vLLM 与 PagedAttention](#/v3/03)）。

> **案例（视频出处：BV1i6Y86AEv3）**
> 24G 单卡塞进 Q6/Q8 高精度权重后，"根本没有空间给到上下文，也没有空间给到并发"。显存就这么多，KV 与并发要在这里抢地盘（这笔 24G 硬跑 256K、KV 压 Q4 的账见 [量化的代价](#/v2/06)）。

### 静态批次 vs 连续批处理

| | 静态批次（static batching） | 连续批处理（continuous batching） |
|---|---|---|
| 组批时机 | 开跑前凑满一批 | 每步迭代后重新组批 |
| 已写完的请求 | 陪最慢的跑完才散批 | 立即退场，释放槽位 |
| 新来的请求 | 排队等下一批 | 下一步就插入 |

静态批次的浪费在"陪跑"：短请求早早写完，槽位却占着不动。连续批处理让调度器（scheduler）每步 decode 后重新挑人组队，配合 [vLLM 与 PagedAttention](#/v3/03) 的分块 KV 管理，新请求随到随插，这是服务级引擎吞吐碾压朴素 server 的主要原因，也是 [推理框架两流派](#/v3/02) 分野的落点。

### batch 抬高吞吐，不抬高单路速度

batch 也是 prefill 的切块单位，甚至能拿来给多卡提速。

> **案例（视频出处：BV1YxjU6qEuw）**
> 单卡同一个核心一次只能吃一个 batch，跑完全部 40 层才轮到下一个；换成双卡 20+20 层流水线，8K prompt 拆出的 4 个 2K batch 就能重叠跑："同时在处理的其实是 4K 的 prompt"，Prefill 提速五到六成；而 decode 是自回归的，前后 20 层必须串行接续、无法这样重叠，实测不加速也不劣化。完整数字账见 [先会看表](#/v3/01)。

所以这笔账要分两栏记：**Decode 阶段并发能近似翻倍总吞吐，每一路分到的输出速度相应下降；Prefill 阶段两路互相摊薄**。多并发 + 长上下文也因此成为"低配多卡堆显存"路线的理论依据：单卡性能不够，用同时服务更多请求来补；流水线重叠的细节见 [双卡怎么放模型](#/v4/06)。如果你只有自己一个用户，batch 帮不了你：看速度，只认单并发。

## 怎么验证

- **llama.cpp**：`llama-server -m 模型.gguf -np 4 -b 2048 -ub 512`，其中 `-np` 是并发槽位数，`-b`/`-ub` 是逻辑 batch 与 ubatch，启动日志会打印 `n_batch`、`n_ubatch`。再用 `llama-bench -np 1,4` 各跑一次同一模型：并发开大后总 tok/s 上涨、单路速度相应下降（对照 [先会看表](#/v3/01) 的 curl 实验），亲手复现本章结论。
- **vLLM**：盯三个启动参数：`--max-num-seqs`（最多同时跑几条请求）、`--max-num-batched-tokens`（一步最多拼多少 token，即 batch 粒度）、`--gpu-memory-utilization`（划给权重+KV+缓冲的显存比例）；跑起来后看日志中 Running 请求数与吞吐，同时观察显存随并发上涨。
- **算一笔账**：沿用 [KV 缓存](#/v1/05) 的案例：双 2080Ti 共 44G = 20G 权重 + 16G KV（256K、FP16）。若开 2 路并发，KV 翻倍成 32G，总账 52G 超出 44G，直接 OOM。所以那套方案只能"单并发吃满上下文"；想多并发，就得砍上下文、压 KV 精度或加卡。把并发参数和显存预算对上。
