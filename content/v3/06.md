## 投机解码：猜对了就赚到

想一个编辑部：主编**写**稿极慢，每写一个字都要翻遍整柜资料；实习生写字飞快但常出错。聪明的安排是让实习生一口气拟四个字，主编只扫一眼，对的留下，从第一个错处截断。审四个字并不比审一个字贵多少，写才贵。于是成稿快了，质量一分没掉。

[Decode 阶段](#/v1/07)就是那位慢主编：[自回归生成](#/v1/02)（Autoregressive）一次只吐一个 [token](#/v1/01)，每吐一个都要把全部几十层权重完整过一遍。**投机解码（Speculative Decoding，又译推测解码）**让便宜的模型先猜、贵的模型只验收，赌的就是"猜对了就赚到"。

### draft-verify：草稿与验收

框架只有两步：

- **draft（起草）**：更轻的草稿模型（draft model）一口气猜出 N 个候选 token；
- **verify（校验）**：主模型一次前向同时核对这 N 个候选，从第一个被拒的位置截断。

校验为什么近乎免费？主模型一次前向本来就能同时算出一段序列里各位置的输出（和 [Prefill 与 Decode](#/v1/07) 里 Prefill 一次并行吞整段输入是同一个道理），验 4 个候选与验 1 个候选的计算量差别很小；Decode 的瓶颈在每步搬一遍权重，不在算，见[带宽决定 Decode、算力决定 Prefill](#/v4/03)。于是**接受率（acceptance rate）**直接决定加速比，直觉一句话：平均猜对几个，每步就多产几个。一次猜 4 个、平均被接受 2 个，每步产出就是这 2 个，再算上在第一个被拒的位置之后主模型免费多出的 1 个，每步从 1 个 token 变 3 个；接受率掉到两成，每步就只剩 1 个出头。加速比怎么算，线性上界与严格式两个公式放在本章末"怎么验证"。

### 任务越确定，赚得越多

什么任务接受率高？"几乎没有第二种写法"的任务：

- **科学计算**：数学题正确答案只有一个，接受率最高，加速最猛；
- **代码工程**：实现路径相对固定，接受率还可以，而 Agent 场景里最多的正是这类负载（写脚本、发起工具调用）；
- **创意写作**：小说散文怎么写都行，输出发散，接受率最低，加速比最小。

> **案例（视频出处：BV1qGh56JEj2）** UP 主砸巨资买显卡，用同一套 prompt 分三类场景、在 SGLang 与 llama.cpp 两个框架上实测（框架背景见[推理框架两流派](#/v3/02)）。SGLang 的加速排名：DSpark 最明显 > MTP > 刚出第二代的 dFlash 最差。UP 主研究 dFlash 一代大半年、本以为早该淘汰，二代实测依旧"快，但那是傻快"。生成快不等于赚，接受率才是分母。

### N 值与甜点区间

一次猜几个（记作 N，DSpark 里叫 gamma）不是越大越好：猜得越多，混进错的概率越大，截断越靠前，白猜的部分还占算力。所以必然存在**甜点区间**。

> **案例（视频出处：BV1qGh56JEj2）** 同一套环境扫 N 值画曲线：llama.cpp 的甜点在一次猜 2/3/4 个；MTP 随 N 增大持续走高，3、4、5 直到 7 都还在涨；DSpark 的峰值落在 5/6/7；而代码场景下 dFlash 与 DSpark 随 N 增大反而下降。框架不同、任务不同，甜点就挪位置，别人的最优 N 不能直接抄。

### 三个流派：MTP、DFlash、DSpark

- **MTP（Multi-Token Prediction，多 token 预测）**：不外挂模型，在主模型 64 层之上原生训练一层专管投机解码的 MTP 层。因为只多一层，显存负担最小；但当前框架在[流水线并行](#/v4/06)（PP）拆分下用不了它。
- **DFlash**：第三方 Z Lab 推出，用扩散模型的方式一次并行产出大量 token（不需要懂扩散，记住"先出一版粗稿、再一步步修"即可），思路类似文生图/文生视频。出字快，但与主模型的匹配率低。
- **DSpark**：厂商归属存疑（视频推测是 DeepSeek），在 DFlash 之上加一层**自回归校正**：DFlash 猜出的 8~10 个候选先交给一个更小的校验层修正一遍，再送主模型验收。又好又快，代价是要额外加载草稿模型，显存占用最高。

> **案例（视频出处：BV1qGh56JEj2）** 巅峰显存对比：dFlash 与 DSpark 都要额外挂一个草稿模型，必然比 MTP 多占一块显存；MTP 只在权重里多一层，最轻量。跑 27B 级模型时 24G 已经不够、32G 可以（单卡多卡均可）。开投机解码前先翻[显存三本账](#/v4/02)，看这块新增开销从哪里扣。

### 代价：Decode 和 Prefill 是两本账

UP 主的原话是"投机解码不是免费的"：它能加速 Decode，却一定会拖慢 Prefill，因为草稿模型或那层 MTP 也要把整段 prompt 过一遍。做长文本吞吐的部署，甚至会干脆把它关掉。投机解码赚的是 Decode 的钱，花的是 Prefill 和显存的钱，哪头划算取决于你的任务确定性；三种方案的多场景实测曲线怎么读，在[MTP/DFlash/DSpark 对比怎么读](#/v5/03)展开。

> **案例（视频出处：BV1XrE26iEMG）** Qwen3.6 27B 稠密 INT8（全重 30 多 GB）在 2080Ti 上的"疯狗模式"实测：明确说明"关了 MTP，所以解码速度不会很快"，Prefill 却冲到纯文本 2500、长代码 2600 tok/s（上一期 FP8 为 1600~1700）。同一条链路关掉投机解码，Decode 与 Prefill 立刻各归各账。Prefill 优先的场景本就不吃这套加速，见[Prefill 与 Decode：吞字与吐字](#/v1/07)。

## 怎么验证

- **查模型有没有 MTP 层**：到模型发布页或 `config.json` 里搜 `mtp`；没有内嵌 MTP 的模型走不了这条路，只能选外挂草稿模型的 DFlash/DSpark 或 EAGLE（另一类投机解码方案）一类。
- **跑一组开关对照**：llama.cpp 用 `-md 草稿.gguf` 挂草稿模型、`--draft-max` 控制 N；开与不开各发一次相同请求，对比返回 JSON 里 `timings.predicted_per_second` 的差值，这个差值就是你机器上最真实的收益。
- **扫 N 值找甜点**：`--draft-max` 取 2、4、6、8 各测一遍，把输出速度画成曲线，峰值即当前任务与硬件的甜点区间，再对照视频的 2/3/4、5/6/7 看偏了多少。
- **反推接受率**：用实测速度除以不开投机解码的基线速度，得到每步平均产出 token 数。加速比两个口径：线性上界 1+N×p；严格式 1+p+…+p^N（接受 0 个仍保底 1 个；p 为接受率）。按线性上界反解接受率，看你的任务落在科学、代码、创意哪一档。
