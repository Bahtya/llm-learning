# 3.3 引擎在忙什么：调度、CUDA Graph 与内核

## 开篇问题

第二部分你帮一套双 2080Ti 方案算过显存账：44G 总盘子装下千问 27B 稠密模型。现在看同一套机器的另一份成绩单：卡不变、模型不变、量化档位不变，单并发吐字速度却从约 50 tok/s 做到 80~100 tok/s（含 MTP 加速）——靠的是一个社区调优的运行时项目，运行一个多月迭代到 v0.1.12，在 GitHub 收获 300 star，还有开发者主动提交代码参与完善（来源：BV14yT46kE5T）。

多出来的速度不是某一个开关按出来的。它藏在三个层面：引擎在请求之间做的决定（排队、组批、KV 管理）、GPU 开始计算之前的空白（内核发射）、真正干活的小程序本身（内核）。还有一个更容易把人带偏的现象：跑推理时任务管理器里总有一两个 CPU 核心钉在 100%，不少人由此得出"换强 CPU 能更快"。本章把一次请求的毫秒逐段拆开，你会看到这一两个核心在忙什么、那段几十毫秒在整条链路里占几成。

核心问题一句话：**同样的卡，换引擎为什么差一倍？**

## 正文

### 先拆清楚：一次请求的时间去了哪

上一章站在用户视角看并发：batch 怎么复用权重、PagedAttention 怎么把 KV 按页分配。本章走进引擎内部，看它每一毫秒在忙什么。全景还是第一章那张链路图，只是现在每个框里都填得上内容了：

```mermaid
graph LR
    A["HTTP 服务器<br/>收请求 / 发响应"] --> B["分词 tokenize<br/>（CPU）"]
    B --> C["排队与组批<br/>（CPU，含 KV 分配）"]
    C --> D["GPU 前向<br/>prefill / decode<br/>几百个内核"]
    D --> E["softmax 与采样、反分词"]
    E --> A
    D -- 每吐一个 token 循环一轮 --> C
```

图中真正花时间的框是 GPU 前向，而它由一段段叫**内核（kernel）**的小程序构成——被上万线程同时执行的一段 GPU 函数。模型一层展开是若干矩阵乘与逐元素运算，每种运算对应一个内核；跑一次前向，就是把几百个内核按固定顺序执行一遍（数量级口径，原资料未给实测计数）。引擎的活分两摊：CPU 侧管排队、组批、KV 管理，GPU 侧执行内核。"换引擎差一倍"的差异，只可能出在这两摊的交界处——要么决定做得不好让 GPU 闲了，要么内核之间和内核本身有可省的空白。

### 排队与组批：引擎每一步都在做决定

请求进来先到队列。vLLM 内部有 waiting 与 running 两个队列：有空闲物理块（上一章的 KV 页）才放行进 running；块耗尽时宁可**抢占（preemption）**——把某个请求踢回 waiting、重算或换出它的 KV——也不让显存爆掉。KV 管理的重要性你在上一章已经算过：8B 级 GQA 模型每 token 约 128KB，按 32K 上限给一个请求预留整块就是 4GB，而 vLLM 论文实测过这类朴素预留的有效利用率只剩两到四成——页管理省下的显存直接换算成并发容量。

组批是另一项每轮都在做的决定：这一步带哪些请求、各分多少 KV、切多长的输入块。单并发时这些决定近乎免费；几十路并发、请求长短不一时，每轮组批与调度本身是 CPU 上的活，工作量随请求数上涨——这里先按下不表，本节末尾的 CPU 一段会给它记上时间账。

你能观察到的结果有两类：并发继续往上加时，新请求的首字时间里多出一段排队等待；发生抢占时，被踢回去的请求总时长暴涨（它的 KV 要重算）。如果你的压测曲线里出现这种孤立的尖峰，先查显存是否逼近上限，而不是先怀疑网络。

### CUDA Graph：把几百次"递单"压成一次回放

现在看 GPU 侧最大的隐形开销。GPU 是手速极快的大厨，CPU 是服务员：每上一道菜，服务员都要单独递一张单子——报菜名（内核入口地址）、报配料（参数）、报取餐口（显存地址）。递单本身有固定耗时，这就是**发射开销（launch overhead）**，公开量级在每次几微秒（原资料未给实测值）。

prefill 对此基本无感：长输入、大 batch 时每个内核都是大菜，一算几毫秒，递单的几微秒九牛一毛。但注意这只是常态而非铁律——短输入、小 batch 的 prefill 也可能落在访存受限的那一侧，判定方法 3.4 给你。decode 正相反：每吐一个 token 都要完整跑一遍前向，此时每个内核只做"矩阵乘向量"级别的小活，微秒级就算完，然后停下来等下一张单子。发射本可与执行重叠，可 decode 的内核太短，GPU 总是先跑完、再干等，重叠不起来——算力全花在"等单"上的空隙里。

**已解示例**：某方案单并发 decode 实测 100 tok/s（含 MTP 加速，双 2080Ti、千问 27B 稠密、batch=1），均摊每个 token 的预算是 1000ms ÷ 100 = 10ms。假设一次前向发射 500 个内核、每次发射 5µs，光递单就是 500 × 5µs = 2.5ms——四分之一的时间 GPU 在干等。这两个输入（内核数与单次发射耗时）都是量级估算而非实测，但结论的形状不变：**内核越碎、batch 越小，发射占比越大**。

**小练习（5 分钟）**：同样的引擎改跑大 batch（比如 32 路），每步内核的执行时间从微秒级涨到接近毫秒级。发射还是那 500 次 × 5µs，算一算发射占比变成了多少，再解释为什么服务端高并发场景很少有人抱怨发射开销。

**CUDA 图（CUDA Graph）**的思路是把菜谱写死：第一次按老办法逐个发射，同时把这一整串内核连同参数、显存地址**捕获（capture）**成一张图；之后每个 token 只发一条**回放（replay）**指令，GPU 照着录像把整条流程跑完。几百次 CPU→GPU 往返压成一次，省下的就是上面的递单时间。

代价记在显存账上。回放要成立，每次执行的地址必须一模一样，所以建图时就得把内核用的**工作区（workspace）**分配好并钉死，还要给单并发、2 并发、4 并发……每种批次档位各录一张图。这块显存从此划走，不能再让给 KV 缓存或更长上下文。它还会约束灵活性：序列长度或并发数超出建图档位，就得补齐到固定长度凑档，或者退回逐个发射的老路。显存极限时这笔账真能压死人：有人盘点百元矿卡时算过，CMP 90HX 单卡只有 10G 显存，跑 27B 低精度权重至少三张卡；就算凑四张共 40G，还要再扣掉每张卡的缓冲空间、CUDA Graph 与运行时，能用的会更小（来源：BV1E5426eE5X）。卡越小、卡越多，被图扣走的那块越疼。

| 场景 | 建议 | 原因 |
| --- | --- | --- |
| 服务级框架跑 decode 为主 | 默认开 | 小内核是大头，整图回放收益最大 |
| 显存极限紧张（小卡、多卡） | 考虑关 | 每张卡都被扣一块，可能直接决定跑不跑得下 |
| 长输入短输出、prefill 为主 | 开关差别不大 | 内核大而少，发射占比本就低 |
| 调试、并发与长度频繁变化 | 关 | 回放要求形状固定，动态形状处处碰壁 |

一句话：**用显存换时延**。这个开关还引出一个工程事实——引擎优化绑定硬件生态，CUDA Graph 是英伟达 CUDA 生态的机制，换 AMD 卡就是另一套名字与另一套内核生态，选卡时得把"我的量化与引擎在这张卡上有没有对应实现"当作一道题（第五部分读规格表时再展开）。

*指标回看 · TPOT：上一章它是"并发摊薄后的每 token 时间"，本章拆出它的第一笔隐形成本——decode 每轮里被发射开销吃掉的毫秒；这笔钱能用显存赎回来一部分。*

### 内核：真正干活的程序，两种快法

消空白只是快的一半，另一半在内核内部。工程上有两条互补的路：把几道工序捏成一道，或者把不必要的工作直接去掉。各有一个代表。

第一个代表是 **Marlin**。量化模型走 weight-only 路线（第二部分讲过记法）：权重按 4/8 位存储，计算前先**反量化（dequantize）**还原成 FP16 再乘——"支持 FP8 权重"与"以 FP8 运算"是两回事，前者只描述存储档位。vLLM 里点名负责这条路线的内核就是 Marlin，它把数据排布、反量化、矩阵乘捏成一道工序喂饱张量核心：快不来自省了计算，而来自少了两道工序之间的显存往返与发射等待。一个直接的应用：社区项目靠它让不支持 FP8 运算的 2080Ti 也能加载 FP8 甚至 FP4 权重——存在档位归存储，运算仍走 FP16（来源：BV14yT46kE5T）。

第二个代表是 **FlashAttention** 一族。注意力计算按朴素写法要把 Q×K 的大矩阵、softmax 的中间结果逐一写回显存再读回来；FlashAttention 把这几步融成一道工序，中间大矩阵不落显存。上下文越长、prefill 越重，省下的显存往返越可观。vLLM/SGLang 等引擎常用的注意力后端库是 FlashInfer，启动日志里的 attention backend 一栏就是在选它。

**已解示例**：判断题——"2080Ti 换成 FP8 权重，prefill 会不会吃到 FP8 硬件加速？"分两步答。第一步问存储还是运算：走 weight-only（Marlin）路线时，FP8 权重先反量化成 FP16 再算，计算仍在 FP16 上，"FP8 运算加速"根本没被使用。第二步问硬件有没有这份能力：2080Ti 不支持 FP8 运算，但支持 INT8 加速，且 INT8 算力是 FP16 的两倍——这是架构设定，不是营销数字；要兑现它，激活值也得是 8 位（W8A8）。当时全生态只有一个量化方案能在这张卡上走通 W8A8，实测 prefill 大大增快、decode 却因实现问题非常慢（来源：BV14yT46kE5T）。结论：**快 = 合适的内核 × 喂得饱的数据 × 用得上的格式**，量化是否提速取决于硬件指令、内核实现、量化粒度与负载阶段，缺一项，纸面翻倍就只是纸面。

**小练习（8 分钟）**：朋友说"我把模型从 GGUF Q4 换成 FP8 权重文件，decode 应该更快，因为数短了"。用本节两步法判断他的推理哪里成立、哪里不成立（提示：decode 的瓶颈在搬运还是计算？他的引擎走的是哪条路线？）。

### CPU 在忙什么：满载的两个核心不是瓶颈信号

回到开篇那个误导性的观察：跑推理时一两个核心钉在 100%。现在你能读懂它了——那是 CPU 侧的分词与调度线程在干活：收请求、对词表切 token、决定组批与 KV 分配、最后把生成的 token 反分词成文本。GPU 侧的重负载（prefill、decode、多卡通信）全不经过 CPU。多卡框架每张卡还挂一个 **TP worker** 进程做协调，所以卡越多、活跃核心越多；"worker 只调度不运算"是从 CPU 视角说的，别误成 worker 不碰计算——每个 worker 进程在自己那张卡上执行 1/N 份权重分片的前向。

这段 CPU 工作值多少时间？低并发下的量级是"几十毫秒甚至更低"。把它放进整条链路算占比：单并发 100 tok/s 吐一段 500 token 的回复要 5 秒，CPU 前期按 50ms 算只占 1%，用户毫无感知。有人算过另一笔账：把 CPU 频率从 1.5GHz 提到 5GHz（约三倍），也只是把几十毫秒压到十几毫秒，对秒级的整段请求可以忽略（来源：BV1qU846JEpW）。最能说明问题的还是那套双 2080Ti 机器本身：主机 CPU 是 i3-9100T，4 核 4 线程、35W 散热设计功耗，配上双通道内存，照样跑出 100+ tok/s（含 MTP）——瓶颈在卡，CPU 够用就行。

那 CPU 什么时候重新上台？请求数与 batch 变多后，分词、组批、调度的工作量随请求数线性上涨，CPU 侧才可能成为瓶颈。所以结论分两半：**单核性能在个人低并发场景几乎不重要；多核性能与多核调度在商业部署才敏感**。攒机时预算的大头留给显卡，这句建议在本章有了毫秒级的依据。

*指标回看 · TTFT：上一章它被排队拉长，本章拆开它的构成——首字时间 ≈ CPU 前期（连接、分词、组批）+ prefill；低并发下 CPU 那几十毫秒不是大头，并发上来后排队与抢占才是 TTFT 尖峰的主要来源。*

### 毫秒分解：给一次请求记一本时间的账

三层都看过了，现在把它们并成一张表。对本地服务发一条流式请求，用 curl 的计时参数就能把时延切成几段：

| 时延段 | 包含什么 | 怎么测 | 本章案例参考量级 |
| --- | --- | --- | --- |
| 连接与前期处理 | HTTP 收包、分词、排队组批 | `curl -w` 的 `%{time_connect}` 起算，首 token 之前减不掉的那段 | 几十 ms 甚至更低（低并发） |
| prefill | 吞下全部输入 token | 首字时间减去前期段；或 prompt 长度 ÷ PP 速度 | 4K prompt ÷ 1700 token/s ≈ 2.4s |
| TTFT | 上两段之和 | `%{time_starttransfer}` | 约 2.4~2.5s |
| decode 全程 | 逐 token 生成 | `%{time_total}` − `%{time_starttransfer}` | 500 token ÷ 100 tok/s ≈ 5s |
| TPOT | decode 每 token 摊到的毫秒 | decode 毫秒 ÷ 输出 token 数 | 10ms（含 MTP） |

这张表是本章的产出物。它的价值不在某一格的数字，而在归因方式：首字慢，先看是前期段（CPU、排队）还是 prefill 段（算力、上下文长度）；吐字慢，先看 TPOT 里发射、KV、带宽各占多少嫌疑。3.4 的瓶颈定位就建立在这张表上。

## 完整算例

**已知条件**：单并发 decode，实测吐字 100 tok/s（含 MTP 加速；双 2080Ti + NVLink、千问 27B 稠密、batch=1，输入与输出长度原资料未说明）；一次前向发射内核约 500 个（量级假设，原资料未给实测计数）；单次发射耗时 5µs（公开量级，原资料未给实测值）。

**要回答的问题**：每吐一个 token 的预算里，发射开销占几成？CUDA Graph 最多能赎回多少？

**公式**：

```
每 token 预算 = 1000ms ÷ 吐字速度（tok/s）
发射总耗时 = 内核数 × 单次发射耗时
发射占比 = 发射总耗时 ÷ 每 token 预算
```

**逐变量解释**：吐字速度决定每个 token 分到多少毫秒（tok/s 的倒数，单位换算成 ms）；内核数乘单次发射耗时得到 CPU 在"递单"上花的总时间，单位 µs，除以 1000 换算成 ms；两者相除得到无单位的占比。

**代入**：

- 每 token 预算 = 1000 ÷ 100 = **10ms**；
- 发射总耗时 = 500 × 5µs = 2500µs = **2.5ms**；
- 发射占比 = 2.5 ÷ 10 = **25%**。

**数量级与单位检查**：µs 乘个数得 µs，再换 ms，量纲闭合。比例检查：decode 单内核执行在微秒量级，与单次发射同数量级，"算一阵、等一阵"的图景成立；同样的 2.5ms 放进 prefill（单内核毫秒级）占比掉到千分之几——两阶段对同一笔开销的敏感度差三个数量级，互相印证。

**口径声明：这是量级估算，不是实测**。500 个内核与 5µs 都是假设输入，结论的形状（占比随内核数线性涨、随批次变大而降）比绝对值可靠。

**误差来源**：其一，内核计数口径——是否把采样、通信、反分词的内核算进去，结果差几成；其二，CUDA Graph 赎回不了全部 2.5ms，回放指令本身仍占一点 CPU 时间，建图那一次也照常逐个发射；其三，部分发射本可与内核执行重叠，重叠得起多少取决于内核长短；其四，不同框架、驱动、CPU 单核性能下，单次发射耗时本身在变。

## 贯穿案例的最终分析

把镜头拉回那套双 2080Ti。全口径先摆齐：双 2080Ti 22G（魔改版）加 NVLink 桥、约 500 元的迷你主机（i3-9100T、双通道内存），跑千问 27B 稠密模型、AWQ INT4 权重（第二部分算过它的显存账）；引擎是基于 vLLM 的社区运行时；负载为单并发 decode，输入与输出长度原资料未说明。成绩：不开 MTP 的裸 decode 约 50 tok/s，开 MTP 后 80~100 tok/s，prefill 约 1700 token/s；同一口径下，一张贵一个数量级的专业卡"可能也就是这个速度"（原始出处见章末资料来源）。

用本章的三层把"差的一倍"拆开看。第一层是调度与 KV 管理：PagedAttention 让 44G 里省出的显存真的装进并发与长上下文，这是上一章的账，属于"跑得起来"的地基。第二层是发射：CUDA Graph 把 decode 每轮的递单压成一次回放，按算例的口径，这笔在 10ms 预算里最多值两毫秒半——不是翻倍的来源，但是"每一毫秒都花在计算上"的前提。第三层是内核：Marlin 让这张不支持 FP8 运算的卡吃上 FP8/FP4 权重的存储收益，尝试 W8A8 路线则展示了"格式对、内核缺、快不起来"的反面。至于 50 到 100 之间最大的一截，来自 MTP（多 token 预测，一种投机解码）——那是下一章的正题，本章只把它挑明：**引擎层的三板斧负责不浪费，投机解码负责凭空多干**，两类提速不要记混。

这个案例还回答了"你要不要自己写运行时"。项目作者一个月迭代到 v0.1.12，改的都是本章这类细账；而对你，判断顺序应该是：先用默认引擎测出毫秒分解表，看空白出在哪一层，再决定换引擎、改配置还是写代码。跳过测量直接调优，等于不看账本就改账。

## 理解检查

1. **计算**：你的方案单并发实测 60 tok/s，一次前向发射约 400 个内核、每次发射 6µs。每 token 预算与发射占比各是多少？若 CUDA Graph 把发射压成一条约 20µs 的回放指令，TPOT 最多降到多少、吐字速度上限变为多少？最后声明你算的是上限口径还是实测口径。
2. **条件变化**：还是这套配置，把并发开到 32 路。每步内核的执行时间明显变长，发射次数近似不变，发射占比往哪个方向变？由此解释为什么 CUDA Graph 在个人单并发场景的口碑远好于服务端。
3. **排障**：同事看到任务管理器一两个核心 100%，坚持"换个强 CPU 推理能快一倍"。用本章的毫秒分解给他算一笔账劝住他；再补一个条件——什么情况下他说得对？
4. **选型**：一张显存只比模型需求多 1G 的卡，服务以 decode 为主。你开不开 CUDA Graph？写出决策依据（提示：图的显存代价、这笔显存还能装几路 KV、跑不跑得下哪个优先）。

## 动手实验

**环境**：Linux，NVIDIA 显卡（6G 显存以上），已装好 vLLM 与一个 7B~8B 级模型（第三部分前两章的压测环境可直接复用）；无 vLLM 环境可改用 SGLang（开关名为 `--disable-cuda-graph`），llama.cpp 新版本在满足条件时自动使用 CUDA Graph、没有对等的命令行开关——各工具参数名可能随版本变化，以官方文档为准。

**步骤与命令**：

```bash
# 1. 基准：默认（CUDA Graph 开）
vllm serve <模型路径> &            # 启动日志找 "Capturing CUDA graphs"
nvidia-smi --query-gpu=memory.used --format=csv   # 记下稳定显存
# 用 3.1 的 curl 脚本测 TPOT：单并发、固定 512 输入、256 输出、测 10 次取均值

# 2. 对照：关闭 CUDA Graph（唯一变量）
vllm serve <模型路径> --enforce-eager &
nvidia-smi --query-gpu=memory.used --format=csv   # 再记显存
# 同一脚本、同参数再测 10 次

# 3. 复算：两次 TPOT 各换算成 ms/token，差值对照 "500×5µs=2.5ms" 的数量级
```

**应记录的项**：模型名与量化档位；两次启动日志关键行；两次稳定显存读数；两组 TPOT（均值与极差）；换算后的 ms/token 差值。

**预期现象**：默认启动时日志逐档位建图，显存比 eager 模式高一块（几百 MB 量级起，随批次档位增多）；关图后 TPOT 变长、显存回落；若你的卡较小、批次档位多，显存差更明显。

**失败排查**：两组数字没差别 → 先确认测的是 decode（单并发、长输出），再确认 `--enforce-eager` 真的生效（看启动日志）；差别远超 2.5ms 量级 → 检查对照组是否混入了并发或输入长度变化；显存不足启动失败 → 降 `--max-model-len` 或减少批次档位后重试；纯 CPU 环境 → 本实验不可做，CUDA Graph 是 GPU 机制，改做纸面复算。

**产出**：毫秒级时延分解表——用正文那张表的框架，填入你自己机器的五个时延段，并在表下写一行结论：你的方案里，CPU 前期、prefill、发射、decode 各自站几成。这张表是 3.4 瓶颈定位的直接输入。
