# 2.3 位宽的世界：浮点、FP8 与整数格

## 开篇问题

上一章末尾留了一个词没拆：位宽。你已经相信"把权重从 16bit 砍到 4bit，显存省四分之三、吐字上限翻四倍"这笔交易划算，但 bit 到底指什么被砍掉，一直是个黑盒。

黑盒先放一放，先看一场更具体的争论。有人在社区晒出项目：一张 2080Ti，2018 年的老卡，跑起了 FP8 甚至 NVFP4 权重的模型。评论区炸锅，反对者的原话大意是：FP8 硬件加速要 40 系以后的卡，NVFP4 是 Blackwell（50 系）的东西，"你连 BF16 都不支持，怎么可能跑 FP8 的权重？"晒卡一面没有魔改硬件，项目确实能跑；反对一方每条硬件常识也都没说错。两拨人说的都是真话，结论却相反。（FP8、NVFP4 是 8 位与 4 位的浮点存储格式，BF16 是 16 位浮点的一种变体，含义本章逐步拆；争论出处见章末资料来源。）

裁决这场争论不需要站队，只需要补齐一块地图：数字在**计算**机里怎么存。地图上三个问题层层递进：一个 16bit 的数被拆成哪几段？砍到 8bit、4bit 时每段怎么重新分账？Q4、IQ1 这些整数档位走的又是哪条路？走完三问，核心问题"**砍位宽到底砍掉了什么**"就有答案，开篇那场争论你也能自己裁。

读完本章你应能交付三件事（章末清单逐条回收）：一页位段解剖笔记；一条 27B 从 FP32 到 4bit 的阶梯账（含与真实文件的偏差核对）；一句判据："支持某格式的权重"与"以该格式**运算**"不是一回事。三问分别在位段、FP8 与整数格、贯穿案例回收。

### 位段解剖：一个数的三段行李

**计算**机里没有"小数点会动的小数"。浮点数（floating point）是科学计数法的二进制版：6.02×10²³ 用三段信息就够了，正负号、有效数字 6.02、指数 23；二进制浮点照搬这个思路，把固定的比特预算切成三段：**符号**（sign，正还是负）、**指数**（exponent，数量级）、**尾数**（mantissa，有效数字）。拆开写：

`值 = (-1)^符号 × 1.尾数 × 2^(指数 - 偏置)`

偏置（bias）是一个固定减数，让指数段也能表达负指数。

二进制下，规格化表示的数（极小的非规格化数除外）尾数第一位一定是 1，这个 1 不用存，叫隐藏位（implicit leading one），白赚一位精度。

用五问盘一遍。解决什么问题：几十个比特要覆盖 10⁻³⁸ 到 10³⁸ 的跨度，定点记法做不到。如何工作：三段各领一份预算，指数决定小数点站在哪，尾数决定有效数字有几位。与"位宽"的关系：位宽从此是一份预算，指数与尾数此消彼长。可观察结果：给指数多拨一位，最大数翻倍但舍入误差变大；反之精度变好、范围变窄。何时失效：超出指数段能力就溢出成无穷大（inf），尾数不够就产生可观测的舍入误差。这两句是后面所有格式的裁判规则。

指数份额决定动态范围（dynamic range，能表示多大和多小），尾数份额决定精度（precision，相邻格子有多密）。这个对应记住了，四种格式不用背，只需要看它们怎么切预算。

### FP32/FP16/BF16/TF32：同一份预算的四种花法

**FP32**（单精度）是通用计算的参考档：1+8+23，范围与精度都宽裕，每个数 4 字节。**FP16**（半精度）把预算砍半：1+5+10，每个数 2 字节，代价是指数只剩 5 位，最大只能表示到 ±65504，再大就溢出；尾数剩 10 位，约合 3 位十进制有效数字。**BF16**（bfloat16）是 Google 为训练设计的切法：指数照抄 FP32 的 8 位，只把尾数砍到 7 位，范围一点不丢，精度让到底。**TF32**（TensorFloat-32）是安培这一代显卡的内部格式：数据按 FP32 进出，张量核心（Tensor Core，硬件里专做矩阵乘加的单元；张量即多维数组）只保留符号与 8 位指数、把 23 位尾数截到 10 位再运算，1+8+10 共 19 位，速度向半精度看齐，动态范围不丢。

四种切法对应四种处境。训练时梯度（每步算出的参数更新量）数值跨度极大，怕的是上溢下溢，不是不够精细，训练界因此选了"范围优先"的 BF16，目前大模型的原生训练精度多就是它。部署时权重训练完就固定，范围已知、不再波动，值得让位给精度和体积，推理界因此从 FP16 起步再往低位宽走。这里埋下第一根桩：**训练精度与部署精度是两码事**。模型卡写着 bfloat16，只说明它怎么生的，不说明你该怎么跑它。

**已解示例**：温度传感器记了 65500 和 70000，都要塞进 16 位。FP16：65500 < 65504 存得下；70000 溢出成 inf。BF16：最大数与 FP32 同级，70000 轻松装下，但尾数只剩 7 位，6 万量级（指数 15 段）相邻格子间距已是 2¹⁵÷2⁷=256，存下的是约数。FP16 怕大数，BF16 不怕大数但记不准，哪个更好取决于数长什么样，没有免检答案。

**小练习**（5 分钟）：0.1 这个数在 FP16 与 FP32 里的存法不同。先写下你的预测：差异来自三段里的哪一段？大概差几位有效数字？动手实验第 3 步会跑 `float(np.float16(0.1))` 和 `float(np.float32(0.1))` 验证。

### 位宽换算力：同一颗核心的三张表

位段还有一层回报：乘法电路的规模大致随位宽平方增长。像竖式乘法，两位数相乘拆 4 次一位数相乘，三位数要 9 次，电路要为"每一位乘每一位"付面积。位宽从 32 砍到 8，同一颗芯片能塞下的乘法器多得多，规格表上常见的"算力逐级翻倍"多半来自这里；附带收益是搬运字节同步变少，带宽压力跟着减半。

规格表上的数字必须按口径读。矿卡 170HX 的解锁风波把这件事放得很大，压进下面这支边栏。

> 矿卡 170HX 与 A100 用同一颗 GA100 核心，出厂被限制算力，单精度 FP32 一栏只有 0.3 TFLOPS（每秒万亿次浮点运算），社区解锁后提升约 31 倍；而 TF32 张量口径的表上写着 100 TOPS（每秒万亿次运算）。两套口径，本书照抄、不互相换算：FP32、TF32、FP16 三张表各列各的，不能互相乘除，官方半精度一栏没列数。容量同样有戏：出厂屏蔽了部分 HBM 显存（高带宽显存），解锁后有 80G 的成功案例、也有人只解到 64G；解锁前 700~800 元、验证成功后涨约 20 倍。规格表的数字由口径决定，装不装得下由容量决定。解锁是社区个案，真实负载能否稳定使用，原资料原话是"还有待观察"，以官方文档与你的实测为准（出处见章末）。

边栏读完，回扣主线一句：看规格表的每个数，先问它"出自哪张表"。

**已解示例**：同事说"我这卡 FP32 算力 20 TFLOPS，你的才 9，我的推理一定更快"。缺两道口径：其一，20 和 9 若不在同一张表上（一个 FP32、一个 TF32 或 FP16），本就不该比；其二，就算同口径，decode 的瓶颈在搬运不在计算（2.2 的账），与吐字速度之间还隔着内核效率、带宽和调度。同口径才可比，可比也不等于推理快。

**小练习**（3 分钟）：翻开你的显卡规格页，找出 FP32 一行和 Tensor 相关的一行算力，写下各自的口径名，确认它们不是同一张表上的数。

### FP8：8 位预算的两种分法

预算砍到 8 位，先看后果：FP8 能表示的数（忽略非数 NaN、无穷大 Inf 等特殊编码）只剩 256 个；FP4 只有 16 个；FP16 有 65536 个。量化做的事，是在连续数轴上立起一排稀疏格子点，再把原数四舍五入到最近格子上。格子越稀，误差越大。

8 位在指数和尾数之间怎么分？标准给了两个答案：

| 格式 | 指数 | 尾数 | 最大值约 | 常见分工 |
|---|---|---|---|---|
| E4M3 | 4 | 3 | ±448 | 权重与前向计算，默认选它 |
| E5M2 | 5 | 2 | ±57344 | 数值波动大、要装得下大数的场合 |

命名就是配置单：E 后是指数位数，M 后是尾数位数，8 位一分不剩。E4M3 格子密、范围窄，适合数值扎堆的权重；E5M2 范围宽、格子稀，适合数值波动大的场合。FP4 推到极端，E2M1 只剩 16 个点，格距粗到没法直接用。NVIDIA 给 NVFP4 的解法是在格子外套两层**缩放因子**（scale，乘回去恢复量级的倍率：4bit 格子只管"分几档"的相对分辨率，绝对量级由它补）：每 16 个数共享一个 FP8 缩放值，再叠一层全张量级缩放，把动态范围从格子外找补回来。格子做不密，就把格子挪到数值最密的地方。

再补上"谁原生支持"：这里指张量核心里真有这种格子的电路，一周期直接算完。FP8 的硬件起点是 Ada（40 系消费卡；数据中心一侧 Hopper 更早），NVFP4 是 Blackwell（50 系）；图灵（20 系）及更早的消费卡没有 FP8 电路；苹果 M3/M4 的低精度矩阵路径未开放，M5 起原生的是低精度矩阵运算（FP16/INT8 口径），FP8 苹果全系仍未支持；AMD AI Max 395（RDNA3.5）不支持 FP8 浮点，整数低精度仍可用。支持矩阵随代际与框架版本变化，以所用框架的官方文档为准。

### 老卡的"支持"：存的是 FP8，算的是 FP16

现在可以回答开篇的争论了，但先把最后一块拼图放上。老卡跑低精度格式的常见形态：权重以 FP8/FP4 位宽**存放**（省显存、省搬运），计算前先**反量化**（dequantize，把低比特格子还原成高精度的数）回 FP16 再运算。钉在墙上的话：**支持 FP8 权重 ≠ 以 FP8 运算**。前者是存储格式，容器和内核认就行；后者要硬件电路，看代际。老卡赚的是搬运减半（2.2 的 decode 上限账），没有算力翻倍。这条路线在 vLLM 里由 Marlin 内核执行（kernel：GPU 上成批执行的计算程序；实现随架构与版本不同，以框架文档为准），记作 W8A16，即 8 位权重、16 位激活值（activation，逐层参与乘法的中间张量），命名下一章展开。

想吃到真翻倍的算力也有路：图灵支持 INT8 加速，社区口径是"INT8 的算力比它的 FP16 还要再翻倍"，8 位比 16 位又短一半。但当时那条整数直算路线（W8A8，8 位权重、8 位激活直接算）实测有一个 bug：prefill 大大增快、decode 却非常慢（模型与输入输出长度等口径原资料未说明）。位宽短了不等于处处变快，中间还隔着内核成熟度（出处见章末）。

把 2.2 的红线再敲一遍：量化是否提速，取决于硬件指令、内核、缩放粒度与负载，位宽只是其中一个变量。老卡与 FP8 的故事就是它的具象版。

### 换一条路：整数格与 Q 档位表

FP8 们走的是"把装小数的格子做小"；另一条路线干脆不装小数。整数量化（integer quantization）把一整块权重先除以一个缩放因子（scale）、四舍五入成整数存下，用的时候再乘回去：

```
存：q = round(w / scale)     # INT8 每参数 1 字节，INT4 0.5 字节
用：w ≈ q × scale
```

打个比方：FP16 是能读出 3.14159 的游标卡尺，INT8 是只有 256 个均匀刻度的尺子，读数是"第几格"，格距 scale 另记一次。边界在于：格距要额外占存储、分块记账会带来零头，马上出现在档位表里；多大范围共用一把尺，先留作尾巴，下一章的超级块专收。模型的本职是"预测下一个 token"这种带随机性的活，这点舍入误差多数时候咬不动结论，体积却能砍掉一半以上。

这条路线在 GGUF（llama.cpp 生态的权重容器格式，量化块、词表、对话模板全部内嵌进一个文件）里长成了一套档位命名，就是你在下载页上看到的那排名字。Q 加数字是平均位宽的标尺：

| 档位 | 名义位宽 | 实测约 bit/参数 | 定位 |
|---|---|---|---|
| Q8_0 | 约 8 bit | ≈8.5 | 几乎无损，常当基准档 |
| Q6_K / Q5_K_M | 5~6 bit | ≈6.6 / ≈5.7 | 质量敏感时的稳妥选择 |
| Q4_K_M | 4~5 bit | ≈4.8 | 社区公认的"标配"甜点档 |
| Q3 / Q2_K | 2~4 bit | ≈3.9 / ≈3.4 | 显存极限下的妥协 |
| IQ1_S 等 IQ 系列 | 1~2 bit 档 | ≈1.5~2 | 极限低比特（i-quants，另一族更激进的记账法），部分老硬件更慢 |

用这张表要认对列。"实测约 bit/参数"是文件口径，比名义位宽多出的零头来自分块 scale 元数据与不做量化的层；反推显存用实测列，别用名义位宽。后缀也有含义：`_K` 指 k-quants，把权重分块、每块各配一把尺子，比"全模型一把尺子"量得准；`_M`/_S/_L 是混合策略，`_M` 把一半注意力张量与 FFN 下投影张量（FFN 即前馈层；哪几类升格、为什么是它们，2.4 细讲）升格到 Q6_K，平均位宽从约 4.5 拉到约 4.8。4.5 的账下一章逐字节推导。

**已解示例**：一个 27B 的 GGUF 文件标着 16.5G，平均每参数多少 bit？16.5×10⁹ × 8 ÷ 27×10⁹ ≈ 4.9 bit。对照档位表，Q4_K_M 实测口径 4.8 基本对上，差约 2%，比 GB 与 GiB 的口径差（约 7%，2.1 的旧账）还小，主要来自社区口径取整与转换器施工单差异；该文件逐张量的位宽分布原资料未说明，不再往下归因。查文件体积先确认单位是 GB 还是 GiB。反着用也成立：想要 4bit 档，体积估 27×4.8÷8 ≈ 16.2G。

## 完整算例

**已知条件**：千问 27B 级稠密模型（2.1、2.2 连用的那只；型号为案例视频口播转写，以模型卡为准，阶梯只依赖参数量，结论与具体型号无关）；十进制 GB 口径（10⁹ 字节）；各档位宽：FP32 32bit、FP16/BF16 16bit、FP8/INT8 8bit、FP4/INT4 4bit。

**要回答的问题**：同一只 27B，从 FP32 一路砍到 4bit，权重体积的整条阶梯长什么样？与真实文件差多少？

**公式**：

```
权重体积（字节）= 参数量 × 位宽 ÷ 8
```

**逐变量解释**：参数量是权重参数的个数（27B 即 27×10⁹ 个）；位宽是每参数比特数；除以 8 换成字节。乘出来的是"权重本体"的数学下限，不含文件里其他内容。

**代入**：

- FP32：27×10⁹ × 32 ÷ 8 = 108×10⁹ 字节 = **108G**；
- FP16/BF16：27×10⁹ × 16 ÷ 8 = **54G**；
- FP8/INT8：27×10⁹ × 8 ÷ 8 = **27G**；
- FP4/INT4：27×10⁹ × 4 ÷ 8 = **13.5G**。

**数量级与单位检查**：参数量是 10⁹ 量级、位宽除以 8 落在 0.5~4 字节，乘积落在 10¹⁰~10¹¹ 字节，与"十几 G 到上百 G"的文件观感同数量级。倍数关系自洽：相邻档位位宽减半、体积减半，四档构成 8:4:2:1 的等比。交叉验证：2.2 用"27B × 2 字节"直接得到 54G，与本表 FP16 一行一致，两条路互相咬合。

**口径声明：这是纸面下限，不是实测值。**真实文件还要装嵌入层权重（词表向量）、个别不做量化的高精度层和分块 scale 元数据。拿两个已知实测对表：GGUF 的 Q4_K_M 约 16.5G（2.1、2.2 都用过它），比 13.5G 高约两成；AWQ INT4 权重 20 多 G（2.2 贯穿案例在用的服务端 4bit 格式），比纸面高出一半。同叫"4bit 档"，实测可差出一截，因为平均位宽与"哪些层不量化"各家做法不同。

**你自己的数字往哪代**（照第一行换上你的模型与文件）：

| 你的模型 | 参数量（×10⁹） | 档位与口径（bit/参数） | 纸面体积（G） | 文件标注（G） | 标注−纸面（%） |
|---|---|---|---|---|---|
| 例：27B FP16 | 27 | 16 | 54 | — | — |
| 例：27B Q4_K_M | 27 | 4.8（实测） | 16.2 | 16.5 | 约 2 |
|  |  |  |  |  |  |

**误差来源**三条：位宽只是平均值，档内波动可到两成；每档有固定元数据开销，参数量越小占比越大；十进制 GB 与二进制 GiB 差约 7%。这张阶梯用来比档间倍数最可靠，绝对值要看具体文件的标称体积，或等 2.5 用你自己的模型实测。

## 贯穿案例的最终分析

回到开篇那场争论（出处见章末资料来源），现在双方每句话都能过秤了。

**第一步，核对质疑方的事实。**FP8 硬件加速确实从 Ada 起（消费卡口径，数据中心 Hopper 更早），NVFP4 确实是 Blackwell 的格式，图灵一代确实没有 BF16（BF16 支持从安培开始）。反对者的硬件常识一条没错。

**第二步，核对项目方的事实。**项目没有魔改硬件，跑的是 vLLM 原生支持路径；其官方文档的 quantization 章节按架构列支持表，图灵在列、更早的 Volta（图灵的上一代）不在。文档证据同样站得住。

**第三步，用本章的两个区分解扣。**双方各说各的词：质疑方说的是"以 FP8 运算"（要 FP8 电路，图灵没有）；项目方说的是"以 FP8 格式存权重"（容器与内核认即可，图灵也有）。拆开这两个短语，矛盾消失：那张卡把权重存成 FP8/FP4 位宽，赚显存与搬运；算之前由 Marlin 内核反量化回 FP16，按 16 位激活值运算（W8A16 路线）。

**第四步，评估这条路线值不值。**图灵没有 FP8 算力可吃，省的是权重体积与 decode 搬运量（2.2 的带宽上限账）；想再吃真算力得换 INT8 的 W8A8 路线，而它当时 prefill 大增、decode 反而非常慢（口径原资料未说明）。所以"2080Ti 跑 FP8"是成立的存储优化，不是算力翻倍，两边的话各自只在自己那半边为真。

第五步，拿同期的另一张卡做对照。170HX 解锁是同一课的强化版：FP32 表上 0.3 TFLOPS、解锁约 31 倍，数字由"读哪张表"决定；HBM 解锁到 80G 让身价涨约 20 倍，能不能装由容量决定。口径、容量、负载三件事各管各的，混着谈就会得出错结论；解锁卡实际可用性，原资料结论是"还有待观察"。

裁决：双方各对一半，错的那一半都出在把"存储位宽"与"运算精度"焊死在一起。到这一步，你可以替任何一方向另一方**解释**清楚，不用站队。

## 理解检查

1. 计算：一个 70B 模型，FP16 与 4bit 档的纸面权重体积各是多少 G？若它的 Q4_K_M 文件实测 39G，平均每参数多少 bit？多出的部分最可能是什么？
2. **条件变化**：要长期存档训练时的梯度，FP16 和 BF16 选哪个？理由必须用"指数/尾数"的语言说（提示：梯度怕上溢下溢，还是怕不够精细？）。换成存训练完的权重，答案会变吗？
3. **排障**：朋友在 20 系卡上用 vLLM 加载 FP8 权重模型成功，但发现速度没有"翻倍"，显存倒是一半了。解释这个现象，并给出一个验证"他的卡实际在什么精度上运算"的思路（提示：W8A16、反量化、框架文档的支持表）。
4. 选型：24G 显存的卡要跑 27B 模型，还要留 4G 给 KV 缓存与计算缓冲，权重预算 20G。FP8 档（纸面 27G）行不行？4bit 档呢？如果只能站在 GGUF 生态里挑，你会找哪个后缀的文件名，预算表怎么列？

## 动手实验

**环境**：任意装了 Python 3 与 NumPy 的机器（CPU 即可，无需显卡）；无 NumPy 先 `pip install numpy`。

**步骤与命令**：

```bash
# 1. 亲手拆开 1.0 的四个字节
python3 -c "import struct; print(struct.pack('>f', 1.0).hex())"
# 输出 3f800000

# 2. 手拆验算：3f800000 = 0 | 01111111 | 00000000000000000000000
#    符号 0；指数 01111111 = 127，减偏置 127 得真指数 0；尾数全零
#    值 = 1.0 × 2^0 = 1.0 —— 三段行李对上了

# 3. 撞一次 FP16 的上界（含预测验证）
python3 - <<'EOF'
import numpy as np
print(np.float16(65504))    # 65504.0
print(np.float16(65520))    # inf
print(float(np.float16(0.1)), float(np.float32(0.1)))
EOF
```

**应记录的项**：第 1 步的十六进制输出与位段拆解过程；第 3 步三行的输出；0.1 的差值（约 2.4×10⁻⁵）与小练习预测的对照，来源是尾数只剩 10 位。

**预期现象**：65504 还在，65520 变 inf。65504 之上格子间距已跳到 32，65520 恰是 65504 与 65536 的中点，四舍五入进 65536 即溢出；65505~65519 仍舍回 65504。溢出那行可能伴随 RuntimeWarning（overflow），这是 NumPy 的溢出警告，属预期，不是环境坏了。0.1 在两种精度下明显不同，是尾数变短的直接后果。

**加餐（可选）**：先别运行，手拆 `struct.pack('>f', 25.0)` 的结果 41c80000（指数 131−127=4，尾数 0.5625，1.5625×16=25），再运行验证。装了 PyTorch 的话，`torch.finfo(torch.float8_e4m3fn).max` 应打印 448.0，与正文表格对表（接口以所用版本官方文档为准）。

**失败排查**：`ModuleNotFoundError: No module named 'numpy'` → `pip install numpy`；`struct.error` → 格式串写错，`'>f'` 的 f 是 4 字节浮点、`>` 是大端序；inf 没出现 → 检查是否误写成 `np.float32`；想交叉验证 → 搜 "IEEE 754 converter" 的在线工具，第三方工具行为以其实际实现为准。

**产出（位段解剖笔记）**：一页笔记，三行内容：其一，0x3F800000 的三段拆解图（自己画）；其二，FP16 溢出实验的输入输出记录；其三，用一句话回答核心问题"砍位宽砍掉了什么"。参考方向：浮点路线先砍尾数（精度），再砍指数（动态范围）；整数路线则连小数格子一起换成"整数格 + 另记的缩放尺子"。2.4 打开 GGUF 时，把这张笔记与超级块的 4.5bit 账对一次。
