## 论断清单

- 投机解码的原理是：用一个更轻的模型先生成一批推测输出，再由主模型（如千问 27B/32B）校验 | 原理推导 | "用一个更轻的模型生成一堆推测的输出值……由主模型来去进行一个校验"（第 24-28 段）
- 当前主流框架提供的投机解码主要有三种：MTP、dFlash（刚出第二代）、DSpark，另有 EAGLE、dFlash 变体 dTree 等不在本次讨论范围 | 经验圈子信息 | "主流框架里面提供的投机解码是三种……一个是 MPP，另外一个是 d flash……deep sig 推出来的 D spark……还有像 ego、dd tree"（第 7-21 段）
- MTP 就是 Multi-Token Prediction：在主模型（64 层）之上单独加一层专门做投机解码的 MTP 层，内嵌在官方主模型里、属于原生训练 | 原理推导 + 圈子信息 | "他是 64 层嘛，然后他 64 层之上前面又单独加了一层专门用于做投机解码……内嵌在官方的主模型里面"（第 35-44 段）
- dFlash 由第三方 Z Lab 推出，用扩散模型方式一次生成非常多的 token，类似文生图/文生视频 | 经验圈子信息 | "第三方主要是 z lab……扩散模型……有点类似于文生图或者文生视频……一下子可以生成非常非常多的 token"（第 47-54 段）
- dFlash 生成快但与主模型的匹配率（接受率）低，因为生成质量差 | 原理推导 + 实测 | "你生成的多生的快……它和主模型的匹配率相对来说就会低……一直以来是速度比较快但是接受率比较低"（第 55-65 段）
- DSpark 是在 dFlash 基础上加一个类似 MTP 的自回归校正层：dFlash 生成的 8~10 个 token 在交给主模型前，先由更小的校验层内部校验/修正，再交主模型校验 | 原理推导 | "他在类似 d flash 的基础上专门有一个机制来校验或者修正……称为叫自回归的校正……递给 27B 主模型之前我先由一层更小的校验层内部校验"（第 76-92 段）
- 投机解码加速效果最明显的条件是：推测值的确定性（唯一性）高、主模型接受率高 | 原理推导 | "在他推测的这个值唯一性非常高的情况下……接受率高的情况下，它的加速就明显"（第 111-116 段）
- 三类场景实测：科学计算接受率最高、加速最快；创意写作最发散、接受率最低、加速比最小；代码工程实现路径比较固定、接受率还可以 | 实测数据 | "接受率最高的就是科学计算，所以它的加速度是最快的……接受度最低的就是创意写作……创意写作是发散的"（第 123-132 段）
- 数学/理科题正确答案只有一个，所以科学计算场景确定性高、加速明显 | 原理推导（类比） | "做数学的是不是正确答案只有一个，所以加速效果就明显"（第 150-153 段）
- Agent 场景里用得最多的是代码场景（脚本撰写、调用、tool call） | 经验圈子信息 | "一般 Agent 场景下最多可能就是在代码场景……包括一些 tool call"（第 159-164 段）
- 同一框架（SGLang）内对比：DSpark 加速最明显（绿线），MTP 其次（蓝线），dFlash 第二代最拉胯（黄线） | 实测数据 | "加速最明显的就是这个 d spark 绿色这条线……蓝色这条线是 MTP……黄这条线就是 d flash 第二代……最拉胯"（第 174-194 段）

- MTP 随推测数量变大仍会不断提升（3、4、5 甚至到 7 都是甜点）；而代码场景下 dFlash 和 DSpark 随 N 增大逐渐下降 | 实测数据 | "发现 NTP 在你的推测数量变大的情况下还是会不断提升……代码情况下不管 d flash 还是 d spark 都会逐渐下降"（第 226-244 段）
- 一次性推测得越多，里面错的概率越大，所以必然存在甜点区间；DSpark 的峰值大约在 5、6、7 | 原理推导 + 实测 | "你推的多也就意味着里面可能错的概率就大，所以一定会有个甜点……DISPARK 可能到 7 左右、567 左右有峰值"（第 234-245 段）
- 投机解码不是免费的：虽然能加速 Decode，但一定会降低 Prefill 的速度 | 原理推导 | "投机解码它不是免费的……虽然能够加速抵扣（Decode），但他肯定会降低你的 PREFU（Prefill）的速度"（第 247-253 段）
- dFlash 和 DSpark 都需要额外加载一个草稿模型，因此必然比 MTP 多占显存；MTP 只在模型权重里多一层、是最轻量的，显存负担最小 | 原理推导 + 实测（巅峰显存占用） | "d flash 跟 d spark 都需要额外加载一个 drafter model（草稿模型）……MTP 只增加一层所以最轻量"（第 261-275 段）

## 知识点候选

- Token 与词表：语言模型以 token 为单位输出 ← 大语言模型基本概念
- 自回归解码（Autoregressive Decoding）：一次前向只吐一个 token、逐 token 输出 ← token
- Decode 阶段的性能瓶颈：为什么解码慢（每步都要完整过一遍大模型）← 自回归解码、模型层数
- Prefill 与 Decode 两阶段：预填充 vs 逐 token 生成，以及各自的速度含义 ← 自回归解码
- 投机解码总体框架：草稿-校验（draft & verify），轻模型起草、主模型验 ← 自回归解码、Decode 瓶颈
- 接受率（acceptance rate）：草稿 token 被主模型采纳的比例，直接决定加速比 ← 投机解码
- MTP（Multi-Token Prediction）：主模型顶层附加一个 MTP 层、原生训练、内嵌权重 ← 模型层数（64 层）、投机解码
- 扩散式文本生成：dFlash 用类似文生图/文生视频的扩散方式一次并行产出大量 token ← 扩散模型、投机解码
- DSpark 的自回归校正：在 dFlash 之上加一层小校验层先内部修正再交主模型 ← dFlash、MTP、接受率
- 任务确定性与接受率的关系：科学计算（答案唯一）> 代码工程（路径固定）> 创意写作（发散）← 接受率
- N 值 / Gamma：一次推测的 token 数量，以及"甜点区间"的存在与成因 ← 投机解码、接受率
- 投机解码的代价：Prefill 变慢 + 显存占用上升 ← Prefill、显存
- 草稿模型（draft model）的额外显存成本：dFlash/DSpark 需额外加载草稿模型，MTP 只多一层 ← 显存、MTP
- 显存容量估算：24G 不够、32G 可跑 27B/32B 级模型（与量化格式相关）← 显存、模型参数量与量化
- 推理框架对比：SGLang（服务端最火）与 llama.cpp（端侧主流）← 本地部署
- 多卡并行方式与投机解码的兼容性：流水线拆分（PP）下可用 DSpark、不可用 MTP ← 流水线并行、显存
- Agent 场景与 tool call：为什么代码场景是 Agent 中最主要的工作负载 ← LLM 应用形态
- 加速比评测方法：同一 prompt 集合、多场景（代码工程/科学计算/创意写作）、画 N 值-加速曲线 ← 上述全部
