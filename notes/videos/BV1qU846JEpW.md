## 论断清单

- 纯 GPU 推理（权重全进显存）+ 低并发场景下，CPU 性能（IPC、频率）对推理速度影响不大 | 原理推导 | "CPU其实对于在纯显卡的情况下的推理，特别是在低并发场景下，它影响不大"
- 推理时看到个别 CPU 核心满载（100%）属正常现象，因为 CPU 只承担分词与调度等固定工作 | 经验观察 | "可能有一两个核心啊，他是满负载的，他肯定就是百分百的这样一个运作"
- 一次请求的完整链路：外层 HTTP Server 收请求 → 文本变 token id（对词表分词）→ 排队调度、按 chunk/batch 分配 KV cache → Prefill 填充 → 逐 token Decode → softmax 出分数 → 采样出 token → detokenize 转文本 → HTTP Server 返回 | 原理推导 | "首先第一步把文本变成token id……把文本进行输出"（第 46-100 段）
- 链路前两步（分词 + 排队调度/批划分）由 CPU 完成；Prefill 和 Decode 这两个重负载阶段由 GPU 完成 | 原理推导 | "前期这两步是CPU他要做的事情……真正的填充跟吐字的这个阶段，这时候就是我们的这个GPU要发挥作用"
- 采用流水线并行或张量并行时会产生多卡通信，而多卡通信的重负载仍然在 GPU 而非 CPU | 原理推导 | "你可能还会产生多卡通信，而多卡通信的这一点它重负载也还是在GPU"
- vLLM 这类框架每多一张卡就多一个 TP worker，它只做双卡调度、不做双卡运算 | 经验圈子信息（vLLM 架构） | "特别像vLLM，它会多一个叫TP worker……进行双卡的调度，但不是进行双卡的运算"
- 显卡数量越多，CPU 上活跃的核心越多（TP worker 进程数随卡数增长） | 经验观察 | "如果说我们卡越多，我们发现我们活跃的这些核心啊，它会越多"
- 低并发（个人 1-2 个并发请求）下 CPU 前期处理时间只有几十毫秒甚至更低 | 量化估算 | "可能我们前期的处理时间啊，可能也就只有个几10ms甚至更低"
- CPU 频率从 1.5GHz 提到 5GHz（提升约 3 倍），也只是把几十毫秒压到十几毫秒，占整个请求耗时比例可忽略 | 量化估算 | "你提升了三倍，那也就相当于把整个几10ms的时间啊，就拉低成为十几毫秒，它对于我们整个请求来说可以说是忽略不计的"
- 高并发下（vLLM 类框架，batch 与请求数变多），CPU 侧处理才可能成为瓶颈 | 原理推导 | "在低并发情况下……没有太大的影响。但是如果在高并发情况下……这个时候可能就会产生一些瓶颈"
- 结论修正：单核性能不重要，多核性能与多核调度在高并发/商业部署时才重要 | 原理推导 | "它单核性能不重要，但是它多核性能、多核调度它可能会比较重要……商业部署情况下，这个东西会更敏感"
- 个人低并发本地部署场景，CPU 影响真的不大 | 原理推导 | "但对于个人来说话，像低并发的情况下，他的影响真的不大"
- 采购建议：预算应优先投给显卡，而不是 CPU | 经验建议 | "博的话最多的预算应该还是要放在显卡里面"
- temperature=0 即贪心采样，直接输出概率最高的 token（如北京 70% 就输出北京） | 原理示例 | "temperature等于零的情况下，贪心采样的情况下，那你直接输出的就是北京"

## 知识点候选

- token / token id ← 分词器（tokenizer）、词表（vocabulary）
- 分词（tokenize）与反 tokenize（detokenize）← token、token id、字符串编码
- 推理框架 ← 客户端/服务器模型、请求-响应
- HTTP Server ← 网络基础（端口、请求/响应）、推理框架
- 排队调度（scheduling）← 并发、队列
- chunk / batch / micro-batch ← token、吞吐与时延
- KV cache ← 自回归生成、注意力机制（Transformer）、显存
- Prefill（预填充）← token、Transformer 前向计算、KV cache
- Decode（逐 token 解码/吐字）← Prefill、自回归生成、KV cache
- 流水线并行（PP）← Transformer 分层、模型切分
- 张量并行（TP）← 矩阵乘法分块、模型切分、多卡通信
- 多卡通信 ← 张量并行、流水线并行、（NVLink/PCIe 概念可补充）
- TP worker ← vLLM、张量并行、多进程
- vLLM ← 推理框架、高并发调度、KV cache 管理
- softmax ← logits、概率分布
- temperature ← softmax、概率分布
- 贪心采样 ← 概率分布、temperature
- 并发（低并发 vs 高并发）← 请求-响应、吞吐量/时延
- 单核性能 / IPC / 频率 / 多核调度 ← CPU 体系结构基础
- 显存容量与模型权重 ← 参数量、精度/量化（可补充，字幕只说"权重塞进显卡"）
- 毫秒级时延分解 ← 请求链路各阶段耗时占比

## 金句与案例

- **"CPU 从 1.5G 升到 5G 也没用"**——CPU 频率提升 3 倍，只把 CPU 侧几十 ms 的前期处理压到十几 ms，对整个请求"忽略不计"（约第 113-118 段）。可作"为什么不该为推理买高主频 CPU"的价格/参数锚点案例。
- **低并发 CPU 耗时基线**——个人场景 1-2 个并发时，分词+调度等 CPU 前期工作仅"几十 ms 甚至更低"（约第 107-109 段）。可与 GPU 生成整段回复的秒级耗时对比，算占比。
- **"一两个核心 100% 但整体很闲"的观察**——推理时常见单个核心满载，由此产生"CPU 越强推理越快"的直觉，up 主明确否定（第 16-27 段）。可作"直觉 vs 实际瓶颈"的翻车式开篇案例。
- **softmax 示例数字**——decode 后 softmax 得到"北京 70%、上海 20%、天津 3%"，temperature=0 贪心采样直接输出"北京"（约第 88-94 段）。可作讲采样策略的入门例子。
- **vLLM 的 TP worker**——每多一张显卡多一个 TP worker 进程，只做双卡调度不做运算，所以卡越多 CPU 活跃核心越多（约第 71-79 段）。可作"CPU 满载≠CPU 是瓶颈"的框架实现案例。
- **多卡通信负载归属**——张量并行/流水线并行带来的多卡通信，重负载仍在 GPU 侧而非 CPU（约第 66-69 段）。
- **结论话术**——"单核性能不重要，多核调度在商业部署才敏感；个人低并发影响真的不大，最多预算放显卡"（约第 125-135 段）。可作本章总结。
