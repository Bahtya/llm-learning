## A. 最严重的 5 个问题（按影响排序）

1. **"带历史→TTFT 变长"的表述与 1.2 刚建立的"前缀复用"结论正面相撞**。"带历史与不带历史"一节断言"历史越长，prefill 要吞的内容越多，第一个字到得越晚"，已解示例进一步写死"决定 TTFT 的上限是这 1260 个 token 的整体，不是那 60 个"——全文无一处提 1.2 实验第 5 步刚教过的"本地引擎普遍复用前缀、第二轮几乎不涨"。读者拿着 1.2 的实测经验来读本节，会得出"两章打架"；拿着本节的断言去做实验，在 Ollama 上测 B2 时结论反转。本章自己教"给结论写条件"，这里却是最该写条件的地方没写。
2. **实验预期"B 组请求后显存占用更高"在常见路径上不成立**。Ollama 类引擎在装载时按上下文上限一次性预分配 KV，单轮请求前后 nvidia-smi 读数常常不动。预期现象写死"显存占用更高"，纯 CPU 之外的多数读者按图索骥会判定"书错了/我测错了"。算例里明明写过"部分引擎对缓存分页或预分配"，实验却没有接上这条自己的口径。
3. **KV 缓存成立理由的因果表述不精确**："K 和 V 只由那个 token 自己决定"。事实是 K、V 由该 token 连同它之前的历史共同算出（经过前面各层），真正成立的原因是因果注意力使它们与"之后生成什么"无关。v1/04 源文即有此简化，但它恰是本章最核心的一步因果，照抄会把初学者引向"表示与上下文无关"的错误迁移，后续学 GQA、滑窗丢弃时都要返工。
4. **术语首现未释 + 查证引导指向歧途**。"AWQ INT4"首现无任何解释（读者只见过 1.1 的"Q4"），"稠密/与 MoE 相对"比 1.2 的同款句少半句；更糟的是口径句"案例型号为口播转写、与 32B 级的层数吻合"——读者若真去查 32B 级模型卡，会发现该档 64 层全是全注意力加 GQA，直接推翻本章"64 层只有 16 层全抄"的故事。这句"吻合"给了读者一个自我否定的核对路径，而全章的核心恰是"教人查证"。
5. **测量方法回退 + 实验第 3 步不可操作**。1.2 已确立用 `curl -w %{time_starttransfer}` 量首字，本章却退回"秒表记录第一个字"，且正文"上一章你用秒表量过的那个数"与 1.2 实际用的命令不符（秒表是 1.1 的方法）；B 组要垫 2000~4000 token 历史，正文只说"垫 2000~4000 token 的历史"，没给把长文塞进 JSON 请求体的任何做法——新手在 shell 引号转义上必然卡死。

## B. 问题 → 具体段落 → 修改策略

1. **段落**："带历史与不带历史"第 2 段、该节已解示例、指标回看标记。**策略**：把性能维度拆成"首字那笔/显存那笔"两笔账并分别给条件——首字那笔可被前缀复用打折（显式回链"1.2 实验第 5 步你见过'第二轮首字节几乎不涨'"），显存那笔不打折；已解示例改为条件句"若三轮前缀是第一次读……若引擎复用了前两轮的前缀……"；指标回看标记补"（前缀复用可部分抵消）"。
2. **段落**：动手实验"预期现象"的"B 组请求后显存占用更高"；算例"这是账面值，不是 nvidia-smi 读数"一句。**策略**：预期现象改为两种剧本都算正常——读数抬升（缓存实际长大）或读数不动（装载时按上限预分配，Ollama 类常见），并把"账面值随长度涨、读数不动"升格为值得记录的口径发现、回链 2.1 的误差解释；算例处同步补"或不动"。
3. **段落**："关键观察"第 2 段首句。**策略**：改为"一个 token 的 K 和 V，由它自己连同它之前的历史一起算出——而这在它进入序列的那一刻就定格了：注意力只'向前看'，后面无论生成什么都不会回头改写它们"。字数几乎不变，因果就位。
4. **段落**："查证"节配置句、贯穿案例"口径与限度"、资料来源口径说明。**策略**：AWQ 补一句"一种 4bit 权重量化格式，与你 1.1 见过的 Q4 档同族"；稠密/MoE 借用 1.2 的成句；"与 32B 级的层数吻合"改为"'64 层'这个数恰与一些 32B 级模型的层数相同，但层型分布以你实际打开的模型卡为准"，并加一句"这个案例的教训在方法不在型号"；匿名对比模型补"口播转写作'解码四'，疑为 Gemma 系列，以模型卡为准"（v1/03、源笔记均有此校正，非新增断言）。
5. **段落**："整体图景"的 TTFT 括号、动手实验步骤 2~3。**策略**：计时统一为 1.2 的 `curl -s -o /dev/null -w "首字节 %{time_starttransfer}s"`（并说明流式下首字节≈首字），"上一章你用秒表量过"改为"用 time_starttransfer 量过"；B 组给出最小可操作的载荷构造——`history.txt` 存长文 + python3 六行生成 `payload_b.json` + `--data @payload_b.json`，注明"没有 python3 就用任何顺手的语言，目标只是得到这个文件"；顺手把 A 组那个无题干的"总结这段话的中心思想"升级为特性——预期现象里写明"模型多半答'你没有给出要总结的文本'，这正是'不带历史则指代无从下手'的现场版"。

## C. 缺失的前置解释、算例、反例、实验条件与来源

- C1 缺 AWQ 一句话解释（来源：v1/05"AWQ INT4，一种 4 bit 量化格式"）；缺 MoE 半句解释（1.2 已有成句可借，规格允许 1.5 才详解）。
- C2 缺"层数"先修锚点："第一章说过，8B 级模型有几十层"——1.1 只列过"层数"这个配置字段名，从未说过"几十层"。修订稿改为"1.1 的模型配置里有个'层数'字段，8B 级在三十多层量级（你装的 qwen3:8b 是 36 层）"，与算例口径声明里的 36 层形成前后呼应。
- C3 缺"第 n 个字生成时历史是 n−1 个"的约定：小练习"第 100 个字那步为多少历史重算"在原稿下 99/100 两可，答案不可检验。修订稿在已解示例前加一句约定。
- C4 缺显存预分配/分页的实验条件（Ollama 按上限预分配；vLLM 按 max-model-len 预分配）：不影响账面公式，但决定读数行为，是"账面值 vs 读数"误差的第一来源，实验必须给两种剧本。
- C5 缺 B 组触发截断的排障项：默认 `num_ctx`（1.2 已提）可能小于垫入历史，长文被静默截断后 B≈A，读者会误判"历史不影响首字"。补一条"B1 与 A 几乎没差别 → 疑似截断，调大窗口或换短文"。
- C6 缺对比模型身份：源笔记校正"解码四→疑为 Gemma 系列/31B"，v1/03 直书"Gemma 60 层"。原稿完全匿名导致读者无法对号查证；修订稿以"口播转写作'解码四'，疑为 Gemma 系列，以模型卡为准"恢复可查性且不新增断言。
- C7 缺显存占用的"指标回看"标记：规格要求指标回看，本章完整算例整节都在算显存，却只有 TTFT 一个标记。补"*指标回看 · 显存占用：1.1 只有粗判；本章第一次能精确算出缓存这一本；总账在 2.1*"。
- C8 缺 1.1 "几千 token 占 0.1~0.3GB"与本章"0.2GB≈1500 token"的口径弥散（前章遗留）：1500~2300 token 与"几千"不符，修订稿加半句"1.1 粗估里的'几千 token'，按精确口径其实只值一两千个 token 的缓存"，完成收窄并注明。
- C9 缺对既有勘误注的保持确认：千问 27B 口播标注、"原资料未说明"清单（GDN 字节数/引擎存储口径/滑窗取值）、64G/16G/120G/20G/100 多 MB/800MB 视频演算值口径——修订稿全部保留，未删未改数。
- C10 数字复核（未发现算错）：32×8×128×2×2=131072B=128KiB ✓；×4096=536870912B≈0.54GB（十进制）✓；4096²/2≈839 万、比值 2048✓；64 层 256K FP16=64GiB、16 层缩至 16G、10/60=1/6 对应 120G→20G ✓；0.2GB÷131072≈1526≈1500 ✓；与 1.4 成稿引用的"1.3 那台 8B 档案 32 层/128 KiB"及 3.2 规格的 128KB/token 完全一致——口径声明必须原样保留（已保留）。
