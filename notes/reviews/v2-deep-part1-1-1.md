## A. 最严重的 5 个问题（按影响排序）

1. **规格三件套整体缺席：token 概念、token 计数、tokenizer 动画**。迁移映射表明确"token 概念与计数进 1.1 必需最小集；BPE 压缩为一段+动画"、tokenizer demo→1.1；outline 学习目标④"数出一个句子的 token 数"、实验"用 tokenizer 数 token"。现稿 token 一词从 mermaid 图开始裸用，全文无定义、无计数、无 `data-demo` 资产（全章 0 个 ill/demo 标签）。更糟的是正文自曝缺口："分词器数据（……本章的 token 计数就靠它）"——本章根本没数。下游已按此依赖写成：1.2"上章已掌握 token 计数"、1.2 算例"约二十个 token"、3.2"权重约 5GB（1.1 的口径）+单 token 值（1.3 的口径）"。主线第一环实际断供。
2. **完整算例的显存公式重复计数，且 KV 区间与 1.3 定稿口径冲突**。公式"权重体积＋词表与配置开销＋KV＋引擎开销"——词表嵌入是权重的一部分、已含在 5.0GB 文件里，单列 0.3~0.6GB 属同一笔钱记两次；"词表约 15 万条目"的出处其实是书页动画里的示意注，不是模型事实（真实数在 config 的 vocab_size，v1/01 口径"十万上下是常态"）。同时"短对话（几千 token）约占 0.1~0.3GB"与 1.3 定稿直接顶牛：1.3 用"第一章短对话缓存约 0.2GB"反推"≈1500 token，即两千 token 以内"——本章写"几千 token"会让读者拿 1.3 的 128 KiB/token 一算就发现书上两处对不上。
3. **两处过绝对/无来源结论**。其一"服务器要同时应付几十路请求，量化省下的显存会被并发消耗吃掉，因此更倾向于原精度配大显存"：源素材（v3/02）只说服务端吃 safetensors 裸权重、"量化由框架加载时自己决定"；"更倾向原精度"还是本章自己推演的因果，且与本书 3.4（2080Ti 跑 16.5GB 权重）、4.1（27B Q4_K_M 双卡）的服务端量化实战相抵触。其二"纯 CPU 环境下速度慢一个数量级"写成实验预期现象，无任何来源（源素材只有 M3 Ultra 对 1080Ti 的跨设备对比），量级实际取决于内存带宽与模型规模。
4. **承诺任务链上两处复现性坑＋产出缺位**。命令清单把 `ollama pull` 放在 `ollama serve` 之前，新装命令行环境的读者第一条就会撞上 connection refused（正文教的三步排查恰好救不了"服务还没起"这一步的最短路径）；环境写"NVIDIA/AMD 显卡更佳"，记录项却只有 `nvidia-smi`，AMD/无独显读者第二步就卡住。规格章末产出"可复现部署脚本＋首次调用记录（T1 一半）"没有对应段落，实验只给命令不给"把它变成交付物"的动作——T1 的这一半悬空。
5. **核心问题未明说＋学习目标从未列出＋吞吐的指标回看缺失**。开篇用四连问代替了规格核心问题"怎么让一个模型在我机器上回答问题？"的正面陈述；能力清单回头引用"四个学习目标"却无处可对；指标回归表规定"吞吐首次观测=1.1（体感）"，本章无任何吞吐标记（1.2 已写"吞吐仍是体感口径"、1.5 写"体感对比这一档"，回看链的第一环不在）。另有小口径：IQ3 换算"3~3.5bit 即约 0.4 字节出头"（3bit=0.375 字节，不足 0.4）、"砍到约三分之一"（16→4~5GB 是四分之一到三分之一）。
